# Testing

- The suite runs on Vitest 5 (`vitest.config.ts`) as four projects: `unit` (`pnpm test:unit`), which never needs Docker, `integration` (`pnpm test:integration`), which runs against a real server, `e2e` (`pnpm test:e2e`), which runs the packed package in a Next app, and `benchmark` (`pnpm test:benchmark`), which asserts the load envelope's floor before a release (see Benchmark). `pnpm test` and `pnpm check` run `unit` and `integration`, so they need Docker unless `NEXTASKING_TEST_REDIS_URL` is set; `pnpm gate` runs those and `e2e`, last; nothing but `pnpm test:benchmark` runs `benchmark`.
- Name a test file after its project: `foo.test.ts` is a unit test, `foo.integration.test.ts` an integration test, `foo.e2e.test.ts` an e2e test, `foo.benchmark.test.ts` a benchmark. The suffix alone decides the project; the `unit` include (`tests/**/*.test.ts`) excludes the other three suffixes by name, so a new suffix goes in its exclude too.
- Collocate a test with the file it tests (`foo.test.ts` or `foo.integration.test.ts` next to `foo.ts`) under `src/`; `tsconfig.build.json` keeps them out of `dist`.
- Put a scenario that crosses modules or processes in `tests/` instead, named as a sentence saying what it proves (`tests/a-server-round-trips-a-value.integration.test.ts`). The shared harness lives there too, named after what it exports.
- Lay out each test body as Arrange / Act / Assert, one blank line between phases; two phases that fuse into one statement share a block, and a phase a test doesn't have is simply absent.

## Integration harness

- `tests/global-setup.ts` starts one container per run with testcontainers and discards it at teardown; every integration test talks to that server.
- The image is `valkey/valkey:9` unless `NEXTASKING_TEST_IMAGE` names another; CI runs the `test` job once per image in its matrix, `valkey/valkey:8`, `valkey/valkey:9`, `redis:7.4` (the server floor) and `redis:8` (`docs/codebase/ci.md`).
- Set `NEXTASKING_TEST_REDIS_URL` to a full URL (credentials, port, `rediss:` included) to run against a server already running instead; no container starts then. An empty variable counts as unset, for both.
- Write an integration test with `integrationTest` from `tests/integration-test.ts` rather than `test` (lint refuses `test` and `it` from `vitest` in `*.integration.test.ts`, `*.e2e.test.ts` and `*.benchmark.test.ts`): it hands the test `redisUrl`, a `keyPrefix` of its own and `expectInvariantViolation`, and checks the test's invariants after it (see Invariants). Put every key the test touches under that prefix, so tests sharing the server never see each other's keys; never build a prefix in the test.
- The test opens its own client on `redisUrl`, with an `error` listener attached before it connects, and closes it in a `finally`, so a failed assertion leaves no open handle. The test's client is a `TestClient` from `tests/with-redis.ts`: a plain `@redis/client` client speaking RESP2, as the driver does, never the driver itself, called with node-redis's own API (`hGetAll`, `zAdd`, `sendCommand`, …). Take it from `withRedis`; `connectedTestClientOf(redisUrl)` opens one alone, for a connection `withRedis` cannot hand (a child process's, a `MONITOR` one), and whoever calls it closes what it got. Read a key's serialized value, binary-safe, with `serializedValueOf` from `tests/engine-test.ts`.
- The engine, the read API, the wake-up wait and `readServerInfo` take a `RedisClient` (`src/redis-client.ts`), the library's own interface, never the test's client: build them on the library client `withRedis(redisUrl, (redis, client) => …)` from `tests/with-redis.ts` hands beside the test's client, or on the one `withRedisClient(redisUrl, (client) => …)` opens alone (a second connection, a blocking one), and keep the test's client for seeding and reading the server. The library client is the driver (`src/node-redis-driver.ts`), the only module of the library that imports `@redis/client`; the tests import it too, for the test's client and for its error classes. `src/node-redis-driver.integration.test.ts` is the contract of that interface (raw RESP2 replies, a batch answering each command, scripts alone, in a batch and after `SCRIPT FLUSH`, the blocking pop); it reaches the implementation through `withRedisClient` only, except for the driver's own lifecycle: a driver destroyed, or reconnected by force then destroyed, while its socket is still connecting leaves no socket open, which it proves on `createNodeRedisDriver` behind a proxy (`liveConnectionCount()`). A test counting round trips spies on the library client's `send` and `sendBatch` with `readTrafficOf(client, read)` from `tests/read-traffic.ts` (`roundTripCount`, the calls of both, and `sentCommands`): each call is one write, which the contract proves for a batch with a script in it by recording what reaches the proxy (`proxy.recordRequestChunks()` returns a reader of the request chunks from then on).
- Cut the connection with `startTcpProxy(redisUrl)` from `tests/tcp-proxy.ts`: point the instance at its `url`; `cut()` resets the live sockets and resets each new connection as soon as it is accepted, `restore()` lets new connections through again, `cutFor(milliseconds)` does both around a wait, and `stop()` goes in the `finally`. The proxy listens on its port from `startTcpProxy` to `stop()`, cut or not, so no other process can take the port during a cut and `restore()` never has to bind it again. The instance sees a connection reset during its handshake (`read ECONNRESET`) where a down server refuses it (`connect ECONNREFUSED`): node-redis takes both through the same reconnect backoff, never becomes ready, and the instance logs the same `connection error` / `connection restored` pair. `stopAnswering()` plays a connection that stops answering without closing: the live sockets stay open and forward nothing, ever again (the proxy keeps reading what their client sends, never forwarding it, so it sees the client close them), and a socket accepted afterwards is held, its handshake unanswered, until `answerAgain()` forwards what it held and lets it through; `acceptedConnectionCount()` counts the connections the proxy let through (a connection reset during a cut is not counted), `resetConnectionCount()` the connections it reset as soon as it accepted them during a cut, `liveConnectionCount()` the connections let through that are still open, and `silencedConnectionCount()` the ones live at `stopAnswering()` that their client has not closed yet. A scenario proving an instance stopped reconnecting reads the accepted and reset counts at the end of its close and again after a window in which nothing must happen, and expects the live count at 0. A scenario that needs every connection of an instance to have given up on the silence waits for `silencedConnectionCount()` to reach 0 before `answerAgain()`, never a fixed sleep: each connection gives up at its own answer bound, counted from its own oldest call. `closeWhenTestFinishes` answers again and restores before it closes. `retarget(url)` plays a failover behind one address: it resets the live sockets, as a dead server does, keeps listening, and sends every connection accepted afterwards to the new target; `targetUrl()` reads the target of the moment. An integration or e2e test that needs a server of its own, one it reconfigures or demotes, starts its own container with `startOwnServer({ serverArguments })` from `tests/own-server.ts`, on the image the matrix cell names (`NEXTASKING_TEST_IMAGE`), which hands back its direct `url`, a `proxy` in front of it, and `stop()`; one with an evicting `maxmemory-policy` uses `startEvictingServer` from `tests/evicting-server.ts` (`isConfigDisabled` renames `CONFIG` away, as a managed service blocks it). A failover scenario starts a primary and a replica with `startPrimaryAndReplica()` from `tests/primary-and-replica.ts`: two containers of the cell's image on a Docker network of their own, the replica replicating straight from the primary, which syncs with no diskless delay; it returns once the first sync is done, with `primaryUrl`, `replicaUrl` and a `proxy` in front of the primary, for the instance. A lossy promotion is two calls around the write to lose: `cutReplication()` points the replica at an unreachable primary (`REPLICAOF 127.0.0.1 1`), so it keeps its data, stays read-only and receives nothing more; `promoteReplica()` stops the primary with no grace (testcontainers' stop, timeout 0), runs `REPLICAOF NO ONE` on the replica and retargets the proxy to it. Before the cut, `await waitUntilReplicaHoldsEveryWriteSoFar()`: it returns once the replica has processed the replication stream up to the primary's `master_repl_offset` read at the call, whoever wrote, and throws with both offsets past its bound (`REPLICA_CATCH_UP_TIMEOUT_IN_MILLISECONDS`, counted among the test's waits). Never a sleep, and never `WAIT` from the test's own connection: `WAIT` waits for that connection's own last write, so from a connection that wrote nothing it answers at once with the replicas linked, whatever they hold. `stop()` records the checker's verdict on the server the proxy targets at that instant. A starter's `stop()` reads that server's stored keys on a connection that never reconnects, within `STORED_KEYS_READ_BOUND_IN_MILLISECONDS` (5 s) from `tests/invariant-violations.ts`: a server that is gone refuses or resets the connection and the check ends at once, one that accepts and stays silent ends it at the bound, and either records `stored keys: the stored keys on <url> could not be read`; then `stop()` still stops the proxy and the containers. Count that bound among the test's waits for each starter `stop()`. The final check on the run's shared server has no bound. Both starters build their containers with `startServerContainer` from `tests/own-server.ts`, and every test that starts a container counts each start among its waits at `SERVER_CONTAINER_START_BOUND_IN_MILLISECONDS`: the files that start a container start it in the same second, at suite start, and under contention a start that takes under a second takes 24 to 47 s. The bound is the log wait (`SERVER_CONTAINER_STARTUP_TIMEOUT_IN_MILLISECONDS`) plus twice testcontainers' own 30 s wait for the ports to be bound to the host, which cannot be configured: a start that fails on that wait alone ("Timed out after 30000ms while waiting for container ports to be bound to the host") starts again once, and any other failure is thrown as it is. testcontainers leaves the container of a start that failed on that wait running, network aliases included, so `startServerContainer` removes it (forced, no grace, with its network endpoint) before it starts again, and removes a second one before it throws: after a retried start, exactly one container of that start exists. A removal that fails is thrown with the port binding timeout in an `AggregateError`, and the start is not tried again. `startPrimaryAndReplica` starts its two containers one after the other, so a failover test counts `PRIMARY_AND_REPLICA_STARTUP_BOUND_IN_MILLISECONDS`, two start bounds and the first sync. The run's shared container (`tests/global-setup.ts`) starts before any test and is outside this rule. Such a test is skipped with `skipIf(providedRedisUrl() !== undefined)`, so `NEXTASKING_TEST_REDIS_URL` still means no Docker.
- Read what an instance leaves on its own `@redis/client` clients, which the library never hands out, by mocking the module in that test file only: `vi.mock("@redis/client", async (importOriginal) => (await import("./recorded-redis-clients.js")).redisClientModuleRecordingClients(await importOriginal()))`. The real clients are created and kept; `listenerCountsByEventOfClientsFor(url)` reads each listener count of every client created for that URL (the proxy's, so the test's own clients are left out). Never add a seam to `src/` for it.
- Make one client wait with no answer by a blocking command on that client, on a key under the test's prefix (`BLPOP <prefix>unanswered 3`). The shared server serves every file running in parallel: a test never sends a server-wide command such as `CLIENT PAUSE` or `DEBUG SLEEP` to it, since the other files' instances would see an outage nobody caused.

- Build the `INFO` and `CONFIG GET` replies a boot reads, and a source answering them that records what it was sent, with `tests/info-replies.ts`.
- A scenario reads what the instance stored on the engine's layout, each run named by its task and its run id: `storedRun(redisUrl, keyPrefix, task, runId)` from `tests/stored-run.ts` (the record's fields as Redis holds them, strings, with `payload` and `errors` parsed beside them), `savedSteps(…)` from `tests/saved-steps.ts`, `storedRunIdentities(redisUrl, keyPrefix)` from `tests/stored-run-identities.ts` (every run stored, as `{ task, runId }`, sorted), and `storedSchedules(redisUrl, keyPrefix)` from `tests/stored-schedules.ts`. Make a firing due with `moveNextFiringTo(redisUrl, keyPrefix, task, plannedInstant)`, which moves the schedule record's `nextFiringAt` and its `schedules` score together; age a run, its dedup entry or its first-found-unknown instant with the `tests/engine-test.ts` helpers, on a context built from the test's own client.
- Cut the reply to one script call with `proxy.cutBeforeReplyTo` and a matcher from `tests/engine-requests.ts`: `isFetchRequest(request, keyPrefix)`, `isFireRequestOf(request, keyPrefix, task)`, or `isSettleRequestOf(request, keyPrefix, { task, runId, settleKind })`. A cut reply proves a lost reply only if the request ran: load the script before arming the cut (one call of the same script from the test, which takes the driver's `NOSCRIPT` fallback), so the cut request is never an `EVALSHA` answered `NOSCRIPT`. They match a script by its keys, built with `engineKeysOf`, never by its SHA or a hand-written key. Hold one call instead with `proxy.holdRequest(matcher)`: unlike `cutBeforeReplyTo`, the request does not reach the server. It resolves with `release()` once a matching request arrives, and that request and every later one on its connection wait until `release()`, while the other connections go through. Arrange a race between workers behind one proxy with it: hold the first worker's call until another worker's call has landed, then release it.
- Prove what an instance sends with `startCommandMonitor(redisUrl)` from `tests/command-monitor.ts`: it resolves once the server monitors, and hands back `monitoredCommands()`, every command monitored so far as `{ args, source }`, and `stop()`, which goes in a `finally`. It keeps the raw lines and parses them on read with `monitoredCommandOf(line)`, so a line it cannot read fails the test that reads it, never the listener, where node-redis would swallow the throw and stop monitoring. Filter what you read by the test's prefix: the server is shared. It reports the commands a script runs too, with `lua` as their source.

## Engine scripts

- The engine lives in `src/engine/`: each Lua script is a TypeScript module exporting its source as a string (`enqueue-script.ts`), never a `.lua` file, because Next bundles the library and a file read at runtime would not ship. The engine prepends the shared library (`lua-library.ts`) and sends the result as a `RedisScript` with `scriptCommandOf` (`src/redis-client.ts`), which checks the key count; the client implementation loads it and owns the `NOSCRIPT` fallback.
- Test each script in one collocated integration file named after its module (`enqueue-script.integration.test.ts`), through the engine method that runs it, against the shared server. Assert on the method's typed reply and on the record and indexes, built with `engineKeysOf` from `src/engine/engine-keys.ts`; never write a key by hand as a string. A run's keys take its task and its run id (`keys.runRecord(task, runId)`), and every member Redis holds for a run (an index, a slot set, a dedup entry, a lock's value) is its stored id, built with `storedRunIdOf(task, runId)` from the same module.
- Write a script test with `engineTest` from `tests/engine-test.ts`: built on `integrationTest`, it hands the body `engine`, `redis`, `keys`, `keyPrefix` and `expectInvariantViolation`. Compare everything stored under the prefix before and after a call that must write nothing with `storedValuesByKeyOf`.
- Make the lock tokens a fetch carries with `freshLockTokensOf(count)` from `tests/lock-tokens.ts`; the caller makes tokens, never the script. It reports each token to the test, so a run the test itself locks is never a run left executing; a token built by hand counts as a worker's. Lock runs for a test with `fetchedLockedRunsOf(context, count, limitsByTask)` from `tests/engine-test.ts`, and expire a lock without waiting with `expireLock(context, task, runId)`, which moves `lockedUntil` and the `locks` score into the past together. Age an ended run with `backdateEndedRun(context, task, runId, duration)`, which moves its `finishedAt`, its read index score and its dedup entry's expiry back together, and a handed-back run with `backdateFirstFoundUnknownAt(context, task, runId, duration)`; the scripts read only the server's clock, so a test never waits out a retention or a dedup window. End many runs of a task with `endRuns(engine, task, runIds, "complete" | "fail")` from `tests/ended-runs.ts`.
- A load scenario draws its randomness from `seededRandomnessOfThisRun()` in `tests/seeded-random.ts` (`random`, `pick`) and passes its `seedMessage` to each assertion, so a failure prints the seed; `NEXTASKING_TEST_SEED` replays it.
- Test a library function no script calls yet with a probe: a script made of `LUA_LIBRARY` and a small body, run with `EVAL` in `lua-library.integration.test.ts`. `engine-keys.integration.test.ts` runs the library's key builders the same way and compares them with `engineKeysOf`; a key shape changes in both or the test fails.
- Read the server's clock with `serverInstantInMillisecondsOf` from `tests/server-instant.ts`, and bound a stored instant between a reading before and after the call. Fake only `Date` (`vi.useFakeTimers({ toFake: ["Date"] })`) to prove an instant does not come from the app's clock.

## Invariants

- Every `integrationTest`, `e2eTest` and `benchmarkTest` checks its invariants in an auto fixture (`tests/invariant-violations.ts`) after the body, its `finally` and every `onTestFinished` closer: the fixture registers its check during its setup, so it runs as the last `onTestFinished`. A violation fails the test with the list, each line naming its invariant. A test body never runs these checks itself.
- The invariants:
  - `stored keys`: the checker. `storedKeyViolationsIn(snapshot, keyPrefix)` from `tests/stored-key-violations.ts` judges one atomic snapshot of the prefix (one script returning every key under the hash tag with its type and content, and the server `TIME`) and lists, as sentences naming each run by its stored id, every way the engine's keys disagree. Each member of an index (`runs:<task>:<state>`, `pending`, `due`, `locks`, a waiting list) has a record in that state, of that task and key, with the score the record gives. Each slot set holds only executing runs of its key, and each executing run, of a limited task or not, is in its key's slot set. Each record is keyed by a stored id of its own task, sits in the read index and the engine structure of its state and nowhere else, and its task is in `tasks`. Each side key of a run (`payload`, `errors`, `steps`) has its record beside it. `schedules` matches the schedule records and their `nextFiringAt`. A key of the wrong type is a violation. Dedup entries are not checked. A load scenario samples `storedKeyViolationsOf(redis, keyPrefix)` during the load, on the same snapshot, and asserts the samples with its `seedMessage`.
  - `run left executing`: a run still executing under a lock the test did not make, that is a record `executing` whose `lockedUntil` is after the snapshot's server time and whose `lockToken` did not come from `freshLockTokensOf`.
  - `worker error`: a `worker error` line, named by its error's message; for an e2e Next process, by the whole JSON line.
  - `process warning`: a warning the Vitest process emits, or a `(node:<pid>) <Name>Warning: …` line in a child's output, named `<Name>: <message>`.
  - `unhandled rejection`: a rejection the Vitest process reports during the test, or an `unhandledRejection: ` line in a child's output (Next's own marker, which the worker process entry writes too), named by the reason's message. The fixture's listeners come off before the recorded list is judged; a rejection or warning arriving after that goes to Vitest, which fails the run.
  - `slow close`: an in-process close or a worker process exit after SIGTERM or SIGINT past the `shutdownTimeout` plus 2 s, or an e2e process `stop()` that had to send SIGKILL.
- Sources report themselves, so a test registers nothing: `createRecordingLogger`, `startWorkerProcess`, the e2e `startNext` and `startStandaloneServer`, `closeNextaskingAndCheckItsDuration`, `freshLockTokensOf`, and `startOwnServer` (with `startEvictingServer` on it), whose `stop()` records the checker's verdict on its own server before stopping it. They find the current test in module scope, so the tests of these three chains run one at a time: never mark one `concurrent`. Each throws when started outside a chain's test, except the recording logger and `freshLockTokensOf`, which unit tests use too and which report to nobody there.
- Give an instance that starts a worker a recording logger: it is how the harness sees its worker errors.
- Close an in-process instance with `closeNextaskingAndCheckItsDuration(nextasking, { shutdownTimeout })` from `tests/close-nextasking-and-check-its-duration.ts`, passing the `shutdownTimeout` its worker started with (the library's default otherwise); lint refuses `closeNextasking` from `src/registry.ts` in `tests/` and in integration tests.
- Declare what the test provokes on purpose with `expectInvariantViolation(invariant, message)`, the exact message of the violation: the test passes with it, fails on any other violation, and fails if the declared one never happens. Build a sentence with `storedRunIdOf` and `engineKeysOf`, or `runLeftExecutingSentenceOf(task, runId)`; read a message the server words (a script error) from the line the test observed. A violation the library leaves behind is a bug to fix, never a declaration.
- Prove that a check fails a test with `testFailingWith(chain, name, expectedFailureMessagesOf, body)` from `tests/test-failing-with.ts`: a `.fails` test records its errors in `onTestFailed`, and the next test of the same `describe` asserts the exact list, so run the whole `describe`.

## Worker loop

- The worker loop (`src/worker-loop.ts`) and the attempt it runs (`src/locked-run-attempt.ts`) are unit-tested against `createInMemoryEngine()` from `tests/in-memory-engine.ts`: the engine over plain data, with the same typed replies as the scripts, no Redis and no Docker. Its declared type lists exactly the methods it implements; add a method to it when the loop starts calling one or a contract case needs it.
- The in-memory engine reads `Date.now()` unless given `now`. Run a loop scenario under `vi.useFakeTimers()`, so `vi.advanceTimersByTimeAsync` moves the loop's ticks and the engine's clock together, and the test reads as a scenario: enqueue three runs, advance, expire a lock, advance.
- Hand the loop `engine.waitForWakeUp` as its wake-up wait: it returns when the engine's wake-up marker is armed, by the same transitions as the scripts, or at its timeout. Never wake the loop by hand.
- Assert on the engine's `calls` (every call with its method and request, so one tick is one `tick` call), on `storedRunOf(task, runId)`, `storedScheduleOf(task)` and `runIdsInState(state)` (the consumer's run ids), and on the lines of `createRecordingLogger()`. `expireLock(task, runId)` moves a lock's expiry into the past, `backdateEndedRun(task, runId, duration)` ages an ended run and `backdateFirstFoundUnknownAt(task, runId, duration)` a handed-back run, as their script-side namesakes do; `holdCalls(method)` keeps that method's calls waiting until `release()`, for a round trip still running. To make the engine answer differently (a lost reply, a rejected call), wrap one method in the scenario rather than adding a switch to the engine.
- Keep the in-memory engine honest with the contract suite: `defineEngineContractTests` in `tests/engine-contract.ts` runs each transition the loop depends on against the in-memory engine (`tests/in-memory-engine.test.ts`) and against the scripts (`tests/engine-contract.integration.test.ts`), through a harness giving the engine, `expireLock`, `backdateEndedRun`, `backdateFirstFoundUnknownAt`, an instant already past, a run's state and the wake-up marker, each run named by its task and its run id. The in-memory engine keys its runs by the same stored id as the scripts. A transition the loop starts relying on gets a contract case in the same PR; where the two engines disagree, the spec decides the script, the contract pins it, and the in-memory engine is corrected.
- Build a loop's or an attempt's definitions with `workerDefinitionsOf(tasks)` from `tests/worker-definitions.ts`.
- Hold handlers where the scenario wants them with `createHandlerGate()` from `tests/handler-gate.ts` (`enter()` in the handler, `release(count)` in the test; `gatedBetweenTwoSteps` and `gatedWithNoStep` are the two handlers a shutdown scenario needs), and prove a stop or a close leaves no rejection unhandled by running it inside `unhandledRejectionsDuring(body)` from `tests/unhandled-rejections.ts`, which returns every reason the process reported.
- When a scenario must prove a promise across the loop and the real scripts (the queue control's idle after `makeRunsDueNow`), start `startWorkerLoop` in the integration project on `createEngine(client, keyPrefix)`, the library client `withRedis(redisUrl, (redis, client) => …)` hands beside the test's client, and the test's prefix, with a short `tickIntervalInMilliseconds`, a `waitForWakeUp` that resolves after a few milliseconds, and `createSimulatedRedisOutage(logger).redisOutage`; stop its fetching and ticking and wait for its attempts in a `finally`.
- Hand the loop or the attempt its Redis outage seam with `createSimulatedRedisOutage(logger)` from `tests/simulated-redis-outage.ts`: the real `createRedisOutage` with a fake ready-wait, and a real outage tracker, so the `connection error` / `connection restored` pair is the one production writes. `startOutage()` and `endOutage()` play the driver's `error` and `ready` events. Make the engine away with `engineAwayDuringOutage(engine, outage, "rejected" | "pending until the outage ends")`: the second is a command written on a connection that stops answering, pending until the connection forces a reconnect, which rejects it. Simulate an out-of-memory reply by wrapping a method to answer `OUT_OF_MEMORY_REPLY`. The loop's engine goes through `outage.engineOnWorkerCalls(engine)` (`startedLoopOf` does it), which notes each call on the real refused-write stretch as the connection notes a worker call, the method's name standing for its commands: a call answered `OUT_OF_MEMORY_REPLY` (rejected, or in a tick's command reply) teaches that name and opens the pair, a call with no refusal is accepted and closes the pair when its name was taught. Never start Redis for an outage scenario of the loop.
- Test the connection module (`src/connection.ts`) and what runs around the loop on its behalf (the instance's boot and close) with `FakeRedisDriver` from `tests/fake-redis-drivers.ts`, never a real server. It fakes the driver (`RedisDriver` from `src/node-redis-driver.ts`), the layer under the connection, so the real deadline, resend, forced reconnect, ready-wait and close of `createRedisConnections` run on it: pass `createFakeRedisDrivers().createDriver` as the third argument of `createRedisConnections(…)`, and read the drivers back in creation order with `createdDrivers()`, the command connection's first. It behaves as node-redis does, and rejects with node-redis's own errors (`DisconnectsClientError`, `ClientClosedError`, `AbortError`) so the real classification runs on it: a command sent while it is not ready is held and written at `becomeReady()`, or rejected by its abort signal; `destroy()` and `forceReconnect()` reject every command held or in flight; `loseConnection(error)` plays a reset (an `error` event, and the commands in flight rejected with it); `startReconnecting()` turns it not ready silently; `isAnswering = false` leaves every command written afterwards unanswered, as a connection that stops answering does. It answers `PING` with `PONG`, the check a connection sends when the instance's other connection gives up on the server. `infoReply` and `configReply` script its replies to `INFO` and `CONFIG`, and `scriptReply` its reply to a script, by the script's name, so the real engine can run on it (any other command rejects with "this fake driver has no reply to …"), `closeReply` is `"answered"` or `"never answered"`, and `sentCommands`, `connectCount`, `forceReconnectCount`, `closeCount` and `destroyCount` record what reached it. Send a command answered by a function of yours with `fakeReplyCommandOf(commandName, reply)`, which is how the engine and the wake-up wait on a fake reach it through a connection's calls: `engineOnFakeDriver(engine, client)` and `wakeUpWaitOnFakeDriver(engine, client)` take the `instanceCalls` or `workerCalls` they are built on; the in-memory `waitForWakeUp` takes a stop signal for that, aborted when the driver loses the connection.
- Expect a tick's command replies with `repliedOf(reply)`, `REPLIED_EMPTY_PROMOTE` and `REPLIED_ONE_RENEWAL` from `tests/tick-replies.ts`.

## Worker processes

- Run a worker in a child process, with `startWorkerProcess` from `tests/worker-process.ts`, when the test must signal, SIGKILL or block it, or needs several workers: a process starts one worker at most. Never install signal handlers in the Vitest process: the child sets `NEXT_MANUAL_SIG_HANDLE`, the in-process workers don't.
- The child runs `tests/worker-process-entry.ts` under `tsx`: it connects through `connection` when the config gives one (a proxy's `url` and a short `giveUpAfter`, to cut the worker alone; its fixture records still go straight to `redisUrl`), applies the `timing` override from `src/worker-timing.ts` (for fast stalls, a 2 s lock renewed at 1.5 s left on a 500 ms tick: a lock no longer than the tick lapses between renewals under load; for a deploy overlap, `supportedRecordVersion: RECORD_VERSION - 1` makes the child an older release, which reads and writes records at that version while the test process and the other children stay at `RECORD_VERSION`; the test writes a run at the older version with `createEngine(client, keyPrefix, RECORD_VERSION - 1)` on the library client, never by overriding the timing in the Vitest process), starts the worker with `startWorkerOptions`, and runs the tasks of `tests/worker-process-tasks.ts`. It writes each unhandled rejection to stderr after an `unhandledRejection: ` marker and keeps running, as `next start` does, so the test fails naming the rejection instead of timing out on a crashed worker. Add a fixture task there; it blocks its own event loop when the test needs it, since a blocked child takes no command. `isFailureNoticeRecorded: true` in the config adds a `runFailed` listener, `FAILURE_NOTICE_RECORDING_LISTENER_NAME`, whose run writes `{ task, runId, reason }` as its fixture record; it is off by default, so no other scenario has a notice run for a `stop()` to cut.
- Dispatch from the test with `createWorkerProcessNextasking` (`tests/worker-process-nextasking.ts`). Assert on the child's `logLines`, parsed from its NDJSON stdout into the same shape as `tests/recording-logger.ts`, its `exited` code and signal, and the records its tasks write (`fixtureRecordsOf`, `tests/fixture-records.ts`). `stop()` it in a `finally`; `stop()` sends SIGKILL, which leaves the runs it held executing under their locks, so a child still holding runs at the end is closed with `kill("SIGTERM")` and its `exited` awaited, the close the slow close invariant times.
- Hold a run of a worker child across a silence of its connections with `logLinesOfARunCompletedInItsFirstAttemptAcrossASilence({ redisUrl, keyPrefix, startWorkerOptions }, silence)` from `tests/run-across-a-silence.ts`: it starts the child behind a proxy with a 1 s `giveUpAfter` and a 6 s lock, dispatches `wait-then-record`, calls `silence({ proxy, workerProcess })` once the run has started, then asserts the run completed in its first attempt with no `attempt aborted: lock lost`, and returns the child's log lines; `connectionLinesOf(lines)` keeps the `connection …` ones. With `concurrency: 1` the blocking connection is idle while the run executes, so the command connection is always the first to give up on the silence.
- Give a test that waits on stalls or shutdowns its own `timeout`.

## E2E harness

- The e2e project proves the library the way a consumer uses it: packed, installed by name, bundled by Next, started from `instrumentation.ts`. Its scenarios, its harness and its fixture app live in `tests/e2e/`; the fixture app, `tests/e2e/fixture-app/`, is the manual's example made real. Its `next.config.ts` is empty unless `NEXTASKING_E2E_STANDALONE=1`, which sets `output: "standalone"` and nothing else, as the manual says it needs; it never sets `serverExternalPackages`, so a missing entry would fail it. Its `register()` writes `app registered` once `startWorker()` has resolved, and its `onWorkerNotStarted` writes `app notified: worker not started` with the error's message as `reason` after a short await, without exiting; the fixture's logger writes `err` as `{}`, so assert on those lines rather than on `err`.
- `tests/e2e/global-setup.ts` runs once per run: it fails unless `dist/` exists (run `pnpm build` first; the gate's `build` stage precedes `test:e2e`), copies the fixture app into a fresh directory under the OS temp dir, `pnpm pack`s the root into that copy as `nextasking.tgz`, installs it with no lockfile, then copies the installed app, symlinks kept, rather than installing twice. It runs `next build` in the first copy, and in the second with `NEXTASKING_E2E_STANDALONE=1`, whose `.next/standalone` it copies out to a directory of its own and deletes the rest, so a standalone scenario never reaches the project's `node_modules`. Then it starts the server exactly as the integration harness does (`NEXTASKING_TEST_IMAGE`, `NEXTASKING_TEST_REDIS_URL`). Teardown stops the server and deletes every copy.
- The harness builds a copy; never run `next` in `tests/e2e/fixture-app` itself. `next build` and `next dev` rewrite `tsconfig.json` and write `next-env.d.ts`, `.next/` and, on recent versions, an `AGENTS.md` into the directory they run in.
- The fixture pins `next` to the floor of the peer range; `NEXTASKING_E2E_NEXT_VERSION` replaces that pin in the copy (`16.4.3`, `latest`). `latest` resolves through pnpm's minimum release age, so it can be one release behind npm's `latest` tag.
- Write a scenario with `e2eTest` from `tests/e2e/e2e-test.ts`: it hands the test `redisUrl`, `keyPrefix`, `fixtureAppDir`, `standaloneAppDir`, and `fixtureAppEnv`, the environment that points the fixture at that server, under that prefix, with the fixture's worker gate on (`NEXTASKING_WORKER=on`); `fixtureAppEnvWithWorkerOff` is the same with the gate off, for a process that only dispatches.
- The fixture lists its scheduled task, `refresh-exchange-rates` (every 5 s), only under `NEXTASKING_E2E_SCHEDULE=on`, so a scenario not about schedules has no firing at all, and none for its `stop()` to cut into a `run left executing`. Without the switch the task still type-checks by name but is not listed: dispatching it fails at runtime. A scenario that needs the schedule, or dispatches that task, takes `fixtureAppEnvWithScheduleOnAndGracefulStop`: `fixtureAppEnv` with the schedule on and `NEXT_MANUAL_SIG_HANDLE=1`, because a firing can be in flight at any stop and only the worker's own SIGTERM handling lets it finish before `next start` exits. Stop such a process in the body and assert its exit is `{ code: 0, signal: null, wasForced: false }`.
- Start every process the scenario needs from the harness, and `stop()` it in a `finally`. Scenarios run one file at a time.
  - `startNext` from `tests/e2e/next-process.ts` runs `next start` or `next dev`, and `startStandaloneServer` runs `node server.js` in the standalone directory, each on a free port, waiting until it answers.
  - Both are a `CapturedProcess` from `tests/e2e/captured-process.ts`: the process output, `exited`, and `stop()`, which sends SIGTERM and returns the exit, forced with SIGKILL after 10 seconds. Its lines go through the same output classifier as a worker process (`tests/process-output-violations.ts`), whose unit cases are lines a real `next start` on the pinned version wrote; a Next release that changes its `unhandledRejection: ` marker silences that invariant without a red test.
- Assert on what a consumer observes: HTTP responses, the process output, and the records the fixture's tasks write under the scenario's prefix (`fixtureRecordsOf` from `tests/fixture-records.ts`). Drive a server action as a browser without JavaScript does, with `submitServerActionForm`.
- Run the project alone with `pnpm build`, then `pnpm test:e2e`; it needs Docker, unless `NEXTASKING_TEST_REDIS_URL` is set, and the npm registry.

## Benchmark

- The benchmark project asserts the floor of the load envelope (#147): its scenarios, its harness and its unit-tested helpers live in `tests/benchmark/`. Run it with `pnpm test:benchmark` before every release (`docs/codebase/ci.md`, Release) and on a change that could slow the engine; it is in neither `check`, `gate` nor CI, and lasts about a minute and a half.
- `tests/benchmark/global-setup.ts` always starts a container of its own on `NEXTASKING_TEST_IMAGE` with `startServerContainer`, and ignores `NEXTASKING_TEST_REDIS_URL`, so the number never depends on what else a server serves: the project always needs Docker. Its files run one at a time (`fileParallelism: false`), so the scenarios never contend with each other.
- Write a benchmark with `benchmarkTest` from `tests/benchmark/benchmark-test.ts`: it hands the test `redisUrl`, a `keyPrefix` and `expectInvariantViolation`, and checks the invariants after the body, as `integrationTest` does, so the check always runs after the throughput is measured and printed. A full benchmark prefix (about 250,000 keys) snapshots in about 2 s; if one grows too heavy for one script call, check the generic invariants without the stored keys rather than raising a bound.
- Drive the library through its public surface only (`createNextasking`, `dispatch`, `emit`, `startWorker`, the read API), as a consumer does: a figure measured below it can hold while the consumer's path regresses. Arrange with the harness (seed ended runs with `endRuns` from `tests/ended-runs.ts`), never measure with it.
- Several workers are several processes, as several `next start` do: start them with `startWorkerProcess({ redisUrl, keyPrefix, definitions: "envelope load" })`, which runs the envelope's 50 tasks and its event from `envelopeDefinitionsOf(writeRecord)` in `tests/benchmark/envelope-definitions.ts` instead of the fixture tasks; the test process builds its dispatching and reading instances on the same definitions. Each handler writes `{ task, runId }` as a `HANDLED_RUNS_RECORD_NAME` fixture record, which the scenario reads to prove every run was handled once.
- Count a read's round trips through the public instance by observing its driver: mock `src/node-redis-driver.js` in that test file only with `nodeRedisDriverModuleRecordingDrivers` from `tests/recorded-redis-drivers.ts`, which returns the real driver and records it by URL, put the reading instance behind a `startTcpProxy` of its own so `driversCreatedFor(proxy.url)` returns its driver alone, and measure each read with `readTrafficOf(driver, read)`. A resent command counts, as it costs one more round trip. Every read of the read API costs at least one round trip, so a read measured at zero fails the scenario: it means the driver was not observed (the connection stopped calling `send` and `sendBatch` on the driver object at call time), not that the read was free. Make every read real from the first cycle (the scenario emits once before its window opens, so `getEvent` reads a real event) rather than exempting one.
- The envelope scenario seeds the 100,000 runs the envelope keeps (1,000 completed and 1,000 failed for each of the 50 tasks, about 10 s) before its load window opens, so a read whose cost grows with the queue fails it.
- Print each measured figure with `throughputLineOf(scenarioName, { runCount, elapsedInMilliseconds })` from `tests/benchmark/throughput.ts`, before asserting it, in the `benchmark: <scenario>: <runs> runs in <seconds> s, <runs/s> runs/s` form a release note takes. `pnpm test:benchmark` passes `--reporter=default`, since the reporter Vitest picks under an agent hides a passing test's output.
- Bound a scenario's wait on the floor itself: a scenario of N runs at a floor of F runs/s waits N / F seconds for them, so a throttled worker fails at the floor's deadline, naming the runs completed, never at the test's timeout. Wait for a queue to drain on the handlers' count and on `unfinishedRunCountIn(await nextasking.countRuns())` from `tests/benchmark/unfinished-run-count.ts` reaching 0: completed runs alone never reach N, since retention prunes them.
- A floor is never lowered, its load never shrunk and its concurrency never raised to make a benchmark pass: a benchmark under its floor is a finding about the engine.
- `one-worker-at-concurrency-50-completes-at-least-500-runs-per-second` ends with tens of thousands of completed runs over the 1,000-run retention cap, by design: it runs at twenty times the envelope's rate, past the 200 runs a worker prunes per second (#219). Never make it wait for the prune.

## Waiting

- Wait for an asynchronous outcome by polling it with `vi.waitFor` (retries a callback until it stops throwing) or `vi.waitUntil` (until it returns a truthy value), each with an explicit `timeout`. A fixed sleep is never a wait: keep one only for a window in which nothing must happen (an idle stretch, an outage, a count of reconnects), never as "this has happened by now".
- Give a test a timeout of at least the sum of the timeouts of the waits it runs one after another, plus 5 s (`waitForLogMessage` waits 10 s unless told otherwise), so a slow wait fails with its own message rather than "Test timed out in 5000ms".
- Arrange any concurrency the test asserts: start concurrent actors together, once each one is connected, since a fresh connection can take hundreds of milliseconds and the first one connected may finish the work alone.
- Judge an upper bound on a duration measured in the test process net of the process's own stall: measure it with `measuredDurationOf(call)` or `measuredRejectionOf(call)` from `tests/measured-duration.ts`, assert the upper bound on `elapsedNetOfStallInMilliseconds` (the elapsed time less the longest event-loop stall of its window) and the lower bound on `elapsedInMilliseconds`. It sees the test process only: a worker child's own stall is not taken off.
- `retry` is 0 in `vitest.config.ts`: a test that only passes on a second try is a failing test.

## Under contention

- Run `pnpm test:integration:contended` five times in a row when a change adds or changes an integration scenario that waits on a reconnect, a deadline, a stall, a shutdown or several connections, or bounds a duration. The ticket's own tests fail in none of the five runs; every run is reported with `uptime` before and after; a failure in another test is named with its first assertion line and added to the tracker, not chased in that PR and not re-run away. A run passed only if it ends with `--test:integration:contended OK--`. It is in neither `check`, `gate` nor CI.
- When measuring on part of the suite, pass the test files' paths explicitly: `vitest run --project integration --exclude <file>` ignores `--exclude` under this projects config.
- It runs the integration project twice at once, each run on a container of its own. A CPU hog does not reproduce the failures the suite shows on a busy machine and a second suite does: what contends is the suite's own work, fresh connections to the containers (about 250 ms instead of 13) and the event loop of a test process opening them (stalls of hundreds of milliseconds instead of tens).
- Killed, it leaves its two runs to end on their own within about a minute, and testcontainers' reaper removes their containers.
