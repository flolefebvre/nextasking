# Prior art: how Inngest and Trigger.dev run their own Redis queues

Research for #124, a child of the map #123 (the way to the 0.2.0 engine spec). The question: how do Inngest's and Trigger.dev's own Redis queues handle leases and fencing, the reaper of expired leases, retention, fairness across keys or tenants, wake-up and delayed work, and what did they learn the hard way that an own nextasking engine should copy or avoid. The answers are compared with the prototype on branch [`prototype/run-engine`](https://github.com/flolefebvre/nextasking/tree/prototype/run-engine), as the map's first comment describes it. This file reports facts; the decisions belong to the design ticket.

## Summary

- **Neither project keeps run history in its Redis queue.** Inngest's queue items are mostly identifiers; run state lives in a separate state store that is deleted at run end and archived to ClickHouse. Trigger.dev's source of truth is Postgres (execution snapshots); Redis holds only queue and concurrency state. nextasking keeps both in Redis, so retention and the read API have no direct prior art here.
- **Leases.** Inngest: a lease is a ULID whose timestamp is the expiry, generated from the worker's own clock, stored in the item and in a per-partition "scavenger index" zset; it rotates on every 15 s renewal of a 30 s lease. Trigger.dev: the run queue has no lease at all; liveness is a heartbeat on a Postgres snapshot, enforced by a delayed job in its redis-worker that each heartbeat pushes back (60 s).
- **Fencing.** Inngest checks the lease ID only on renewal; requeue and dequeue do not check it. A generation counter was added later so that a stale peeked copy cannot be leased. Step results are first-write-wins per step ID. Trigger.dev fences on the snapshot ID ("check that the passed in `snapshotId` matches the current"), under a Redlock run lock.
- **Reapers.** Inngest has one scavenger per queue shard, elected by a role lease, every 30 s, in batches of 100, with a random offset into the backlog of expired partitions, and a per-item `ScavengeCount`. Trigger.dev needed two reconcilers after the fact: a mark-and-sweep "concurrency sweeper" for runs leaked in its concurrency sets, and a Redis-versus-Postgres "queue monitor" after an incident stranded runs.
- **Both leaked concurrency.** Trigger.dev's concurrency sets leak "for whatever reason" (PR #2206); it now reconciles them even inside the dequeue Lua. Inngest deadlocked runs whose concurrency permit outlived their lease (PR #5132). The prototype's rule, "the slot lives and dies with the lease", is what both lacked.
- **Non-atomic hand-off stranded runs.** Trigger.dev's dequeue is a Lua move into the concurrency set, then a separate `RPUSH` to a worker list, then a `BLPOP` and a `GET`. Engine crashes in September 2025 left runs "removed from Redis without being moved to `PENDING_EXECUTING`". The prototype's fetch, done in one script with a token, avoids this by construction.
- **Clocks.** Both take time mostly from the client: Inngest has no `TIME` call in any Lua script; Trigger.dev passes `Date.now()` and calls `TIME` in a few scripts. They tolerate skew with long leases. The prototype's Redis `TIME` is stricter than either.
- **Lost replies.** Neither queue's scripts are idempotent under a resend. Inngest's client (rueidis) does not resend write commands by default, so a lost reply becomes an error and the lease expiry recovers it. Trigger.dev's redis-worker sets ioredis `maxRetriesPerRequest: 20`. The prototype's idempotent fetch and settle go further than both.
- **Fairness.** Inngest: a queue per function (partition), a global zset of partitions scored by their earliest item, account-level zsets, short partition leases (4 s), and a weighted random shuffle of what each worker peeks. Trigger.dev: a weighted shuffle of environments and queues with tunable biases, and a Deficit Round Robin scheduler in the newer FairQueue. Inngest's "key queues" (a queue per custom concurrency key) cut throughput when cardinality exploded (October 2024).
- **Wake-up and delays.** Inngest polls every 10 ms and has no blocking pop. Trigger.dev blocks on `BLPOP` of worker lists, outside Lua, and moves due work into them from debounced jobs (500 ms). In both, a delay is just a future score in the same sorted set as ready work.
- **The hard lesson about Redis itself.** Inngest is moving its queue from Valkey to FoundationDB (posts of August and September 2026): "When a Valkey cluster runs out of memory, the whole cluster goes down", whatever "hadn't been persisted is gone", and the single thread caps fairness.

## 1. Inngest

### 1.1 Layout

- **[docs]** "each function you add must get its own queue to maximize fairness", and a higher-level queue "records each function's earliest available job"; "All workers scan this queue to discover available work" ([Building the Inngest queue, part I](https://www.inngest.com/blog/building-the-inngest-queue-pt-i-fairness-multi-tenancy), 2024-01-22).
- **[code]** One hash holds every queue item as a JSON value (`queue:item`). Each partition has a ready zset scored by the item's due time, a global partition zset and an account-level zset point at partitions, scored by their earliest item ([I:`.../lua/queue/requeue.lua`](https://github.com/inngest/inngest/blob/8ffc717d61035d178b14007858687bbd7195764a/pkg/execution/state/redis_state/lua/queue/requeue.lua)). Newer "shadow partitions" and "backlogs" add a stage before the ready queue for constraint handling.
- **[code]** All queue keys of a queue shard share one hash tag, `{<queueDefaultKey>}` ([I:`key_generator.go#L283`](https://github.com/inngest/inngest/blob/8ffc717d61035d178b14007858687bbd7195764a/pkg/execution/state/redis_state/key_generator.go#L283)); the queue client is called `unshardedRc`. Run state keys are tagged per run or account instead, so state and queue sit on different slots or instances. Inngest scales the queue with several separate Redis deployments ("queue shards"), each account assigned to one; executors claim shards with shard leases ([I:`queue/shard_lease.go`](https://github.com/inngest/inngest/blob/8ffc717d61035d178b14007858687bbd7195764a/pkg/execution/queue/shard_lease.go)).
- **[docs]** Shard assignment "was static and manual. Growing capacity meant provisioning new Valkey clusters by hand" ([Migration to FoundationDB, part 1](https://www.inngest.com/blog/migration-to-foundationdb-part-1), 2026-08-24). The October 2024 retros describe building tooling "to migrate accounts across queue shards" after CPU on the primary shard spiked ([2024-10 queue retros](https://www.inngest.com/blog/2024-10-queue-retros)).

### 1.2 Leases and fencing

- **[code]** A lease ID is a ULID created in Go with `ulid.Timestamp(now.Add(leaseDuration))`: the expiry is encoded in the ID, from the worker's clock ([I:`queue.go#L917`](https://github.com/inngest/inngest/blob/8ffc717d61035d178b14007858687bbd7195764a/pkg/execution/state/redis_state/queue.go#L917)). The `lease` script refuses when the current lease's decoded time is still after `currentTime`, an argument from the caller ([I:`lua/queue/lease.lua#L42`](https://github.com/inngest/inngest/blob/8ffc717d61035d178b14007858687bbd7195764a/pkg/execution/state/redis_state/lua/queue/lease.lua#L42)). No Lua script in `redis_state/lua` calls `TIME`.
- **[code]** The lease is 30 s, renewed every 15 s by a background ticker ([I:`queue/consts.go#L65`](https://github.com/inngest/inngest/blob/8ffc717d61035d178b14007858687bbd7195764a/pkg/execution/queue/consts.go#L65), [I:`queue/process.go#L122`](https://github.com/inngest/inngest/blob/8ffc717d61035d178b14007858687bbd7195764a/pkg/execution/queue/process.go#L122)). Each renewal writes a new ULID; `extendLease` returns "lease mismatch" unless the caller passes the current one ([I:`lua/queue/extendLease.lua#L37`](https://github.com/inngest/inngest/blob/8ffc717d61035d178b14007858687bbd7195764a/pkg/execution/state/redis_state/lua/queue/extendLease.lua#L37)). Any renewal error stops the processing of the item ("always stop processing the queue item if lease cannot be extended").
- **[code]** `requeue` and `dequeue` take no lease ID and do not check one ([I:`lua/queue/requeue.lua`](https://github.com/inngest/inngest/blob/8ffc717d61035d178b14007858687bbd7195764a/pkg/execution/state/redis_state/lua/queue/requeue.lua), [I:`lua/queue/dequeue.lua#L52`](https://github.com/inngest/inngest/blob/8ffc717d61035d178b14007858687bbd7195764a/pkg/execution/state/redis_state/lua/queue/dequeue.lua#L52)). `requeue` overwrites the item with the JSON the caller serialized. Fencing at the queue level is therefore only on lease and renewal.
- **[code]** A `GenerationID` was added later: "a monotonic counter bumped by Requeue; mismatch fences a stale dispatch" ([I:`queue/item.go#L106`](https://github.com/inngest/inngest/blob/8ffc717d61035d178b14007858687bbd7195764a/pkg/execution/queue/item.go#L106)). `lease` refuses a peeked copy whose generation is not the item's: "A buffered/peeked snapshot superseded by requeue must not dispatch old data" ([I:`lua/queue/lease.lua#L49`](https://github.com/inngest/inngest/blob/8ffc717d61035d178b14007858687bbd7195764a/pkg/execution/state/redis_state/lua/queue/lease.lua#L49)).
- **[code]** Fencing of results happens in the state store instead: `saveResponse` refuses a second output for a step ID (`HEXISTS`), and treats an identical one as an idempotent save ([I:`lua/saveResponse.lua#L23`](https://github.com/inngest/inngest/blob/8ffc717d61035d178b14007858687bbd7195764a/pkg/execution/state/redis_state/lua/saveResponse.lua#L23)). Two executions of one step can both run; only the first output is kept.
- **[code]** The concurrency reservation ("capacity lease", in a separate Constraint API) has its own renewal, and the worker cancels the work when that lease reaches its expiry before a renewal succeeds: "relying only on its eventual response can allow work to continue after the concurrency reservation has been scavenged" ([I:`queue/process.go#L248`](https://github.com/inngest/inngest/blob/8ffc717d61035d178b14007858687bbd7195764a/pkg/execution/queue/process.go#L248)).
- **[docs]** Keeping the permit apart from the lease bit them: a start job "releases its capacity lease before starting successfully. Ordinary release deliberately keeps the run's manual permit, but removes the lease record and scavenger entry. The retry is blocked by its own retained usage, and the scavenger has nothing left to reclaim" ([PR #5132](https://github.com/inngest/inngest/pull/5132), merged 2026-10-29). The fix records which request owns the permit so a retry of the same run can reuse it.

### 1.3 The scavenger

- **[code]** Leasing an item removes it from the ready zset and adds it to a per-partition scavenger index scored by lease expiry; a global zset points at partitions by their earliest lease ([I:`lua/queue/lease.lua`](https://github.com/inngest/inngest/blob/8ffc717d61035d178b14007858687bbd7195764a/pkg/execution/state/redis_state/lua/queue/lease.lua)). Requeue and dequeue remove the item from the index and re-score the pointer in the same script. The index replaced an older one in a rolling switch ([PR #3404](https://github.com/inngest/inngest/pull/3404)).
- **[code]** The scavenger is a "queue role": one processor per shard holds it through a role lease (10 s), and it runs every 30 s ([I:`queue/scavenger.go#L11`](https://github.com/inngest/inngest/blob/8ffc717d61035d178b14007858687bbd7195764a/pkg/execution/queue/scavenger.go#L11), [I:`queue/role.go`](https://github.com/inngest/inngest/blob/8ffc717d61035d178b14007858687bbd7195764a/pkg/execution/queue/role.go)).
- **[code]** Each pass counts the expired partitions, starts at a random offset when there are more than the batch limit of 100, reads up to 100 expired items per partition, requeues each one with `ScavengeCount++`, and drops index entries whose item is missing "to prevent spinning on this item" ([I:`queue_scavenge.go`](https://github.com/inngest/inngest/blob/8ffc717d61035d178b14007858687bbd7195764a/pkg/execution/state/redis_state/queue_scavenge.go)). This loop runs in Go, one command at a time, not in one script. `ScavengeCount` was added for "alerting on items with excessive scavenge counts" and possible backoff ([PR #3799](https://github.com/inngest/inngest/pull/3799), 2026-03-04).

### 1.4 Idempotent enqueue, retention

- **[code]** Item IDs are deterministic: `HashID` is an xxhash of a job ID ([I:`queue/item.go#L670`](https://github.com/inngest/inngest/blob/8ffc717d61035d178b14007858687bbd7195764a/pkg/execution/queue/item.go#L670)). `enqueue` returns "exists" when the item is present or when a `seen:<key>` tombstone exists ([I:`lua/queue/enqueue.lua`](https://github.com/inngest/inngest/blob/8ffc717d61035d178b14007858687bbd7195764a/pkg/execution/state/redis_state/lua/queue/enqueue.lua)).
- **[code]** `dequeue` deletes the item at once (`HDEL`) and writes that tombstone with `SETEX`, 12 h by default ([I:`lua/queue/dequeue.lua#L62`](https://github.com/inngest/inngest/blob/8ffc717d61035d178b14007858687bbd7195764a/pkg/execution/state/redis_state/lua/queue/dequeue.lua#L62), [I:`queue/consts.go#L126`](https://github.com/inngest/inngest/blob/8ffc717d61035d178b14007858687bbd7195764a/pkg/execution/queue/consts.go#L126)). A finished job leaves only its tombstone in the queue.
- **[docs]** "Enqueuing must be idempotent, as event streams are at least once" (part I). The state store "holds each run's memoized step results" and is archived to ClickHouse when the run ends; queue items "are mostly identifiers that point to the run" ([The queue is the easy part](https://www.inngest.com/blog/the-queue-is-the-easy-part), 2026-09-09).

### 1.5 Fairness

- **[code]** Peeked partitions and accounts are put in a weighted random order (`sampleuv.NewWeighted`), with priority as weight ([I:`queue.go#L1636`](https://github.com/inngest/inngest/blob/8ffc717d61035d178b14007858687bbd7195764a/pkg/execution/state/redis_state/queue.go#L1636)). A worker then leases the partition for 4 s before reading its items ([I:`queue/consts.go#L23`](https://github.com/inngest/inngest/blob/8ffc717d61035d178b14007858687bbd7195764a/pkg/execution/queue/consts.go#L23)).
- **[code]** Backlogs that continue existing runs get ten times the weight of backlogs of new runs, "to ensure queue items to finalize existing functions have a higher likelihood of being refilled" ([I:`queue/backlog.go#L390`](https://github.com/inngest/inngest/blob/8ffc717d61035d178b14007858687bbd7195764a/pkg/execution/queue/backlog.go#L390)).
- **[code]** A partition blocked by its concurrency limit is pushed back 5 s (throttle 1 s, paused 5 min) ([I:`queue/consts.go`](https://github.com/inngest/inngest/blob/8ffc717d61035d178b14007858687bbd7195764a/pkg/execution/queue/consts.go)). Releasing capacity can wake the partition: `capacityReleased` brings the pointer back to the earliest ready item and sets a flag so the next scan ignores the cached "exhausted" state ([I:`lua/queue/capacityReleased.lua#L33`](https://github.com/inngest/inngest/blob/8ffc717d61035d178b14007858687bbd7195764a/pkg/execution/state/redis_state/lua/queue/capacityReleased.lua#L33)).
- **[docs]** Key queues, a queue per custom concurrency key, made throughput collapse at high cardinality: "Processing each individual queue requires 4x the number of operations than processing an individual queue item", and most queues held one or a few items (2024-10-04 in the [October 2024 retros](https://www.inngest.com/blog/2024-10-queue-retros)).
- **[docs]** The single thread caps fairness: the queue reads at most 2,000 items per pass, and when many are blocked by limits the useful throughput per pass drops; "Lock it down to stay consistent and you've traded a fairness bug for a latency bug" (The queue is the easy part).

### 1.6 Wake-up and delayed work

- **[code]** The processor polls every 10 ms by default ([I:`queue/consts.go#L122`](https://github.com/inngest/inngest/blob/8ffc717d61035d178b14007858687bbd7195764a/pkg/execution/queue/consts.go#L122)); there is no blocking pop. A delayed job, a sleep or a backoff is a queue item whose score is in the future; partitions are scored by their earliest item, and workers peek a window up to now plus a lookahead of 1 s.

### 1.7 Lost replies

- **[docs]** rueidis retries only read-only commands by default; write commands are retried only when marked `ToRetryable`, "Make sure you only use this feature with idempotent operations" (rueidis README, via ctx7 `/redis/rueidis`).
- **[code]** No Inngest code marks a command retryable (no `ToRetryable` in `pkg/`). A lost reply to `lease` therefore surfaces as an error; the item stays leased until its lease expires and the scavenger requeues it. A lost reply to `extendLease` makes the next renewal fail with "lease mismatch", and the worker stops the item.

### 1.8 Redis itself

- **[docs]** "When a Valkey cluster runs out of memory, the whole cluster goes down, not just the tenant that pushed it over the edge." "In-memory storage also means durability is only ever as good as our replication and persistence setup": whatever "hadn't been persisted is gone", and recovery depends on restoring a stateful cluster, "not on how quickly we can fail over" (Migration to FoundationDB, part 1). The queue still runs on Valkey at the time of the September post.

## 2. Trigger.dev

### 2.1 Layout

- **[docs]** "The execution state of a run is stored in the `TaskRunExecutionSnapshot` table in Postgres." Run operations are serialized with a Redlock lock because "Postgres locking is not enough on its own because we have multiple API instances and Redis is used for the queue" ([T:`internal-packages/run-engine/README.md`](https://github.com/triggerdotdev/trigger.dev/blob/41ad1995b30573a9b55cfaab80c3293b7c35c1f8/internal-packages/run-engine/README.md), sections "Run locking" and "Run execution").
- **[code]** The run queue has three stages. A message key holds the payload; each queue is a zset scored by availability time; sharded "master queues" are zsets of queues. A master-queue consumer runs `dequeueMessagesFromQueue`, a Lua script that checks environment and queue limits with `SCARD` of concurrency sets, removes due messages from the queue zset and `SADD`s them to the concurrency sets ([T:`run-queue/index.ts#L6227`](https://github.com/triggerdotdev/trigger.dev/blob/41ad1995b30573a9b55cfaab80c3293b7c35c1f8/internal-packages/run-engine/src/run-queue/index.ts#L6227)). Node then `RPUSH`es the message keys onto worker-queue lists in a separate pipeline ([T:`#L3559`](https://github.com/triggerdotdev/trigger.dev/blob/41ad1995b30573a9b55cfaab80c3293b7c35c1f8/internal-packages/run-engine/src/run-queue/index.ts#L3559)). A worker `BLPOP`s a list ([T:`#L4441`](https://github.com/triggerdotdev/trigger.dev/blob/41ad1995b30573a9b55cfaab80c3293b7c35c1f8/internal-packages/run-engine/src/run-queue/index.ts#L4441)) and then reads the message key.
- **[code]** Keys carry a hash tag per organization, `{org:<id>}` ([T:`run-queue/keyProducer.ts#L448`](https://github.com/triggerdotdev/trigger.dev/blob/41ad1995b30573a9b55cfaab80c3293b7c35c1f8/internal-packages/run-engine/src/run-queue/keyProducer.ts#L448)). The dequeue script also writes the master queue key, which is not under that tag, so the scripts as written cannot run across Cluster slots (inference from the key list, not stated in the code).

### 2.2 Leases, fencing and stall recovery

- **[code]** The run queue holds no lease. Liveness is a heartbeat on the Postgres snapshot, with timeouts of 60 s for `PENDING_EXECUTING`, `EXECUTING` and `EXECUTING_WITH_WAITPOINTS`, 10 min for `SUSPENDED` ([T:`engine/index.ts#L410`](https://github.com/triggerdotdev/trigger.dev/blob/41ad1995b30573a9b55cfaab80c3293b7c35c1f8/internal-packages/run-engine/src/engine/index.ts#L410)). The deadline is a delayed job `heartbeatSnapshot.<runId>` in redis-worker that each heartbeat reschedules ([T:`executionSnapshotSystem.ts#L713`](https://github.com/triggerdotdev/trigger.dev/blob/41ad1995b30573a9b55cfaab80c3293b7c35c1f8/internal-packages/run-engine/src/engine/systems/executionSnapshotSystem.ts#L713)).
- **[code]** Fencing is the snapshot ID. A heartbeat or a stall handler that does not carry the latest snapshot ID stops ([T:`executionSnapshotSystem.ts#L729`](https://github.com/triggerdotdev/trigger.dev/blob/41ad1995b30573a9b55cfaab80c3293b7c35c1f8/internal-packages/run-engine/src/engine/systems/executionSnapshotSystem.ts#L729), [T:`engine/index.ts#L2801`](https://github.com/triggerdotdev/trigger.dev/blob/41ad1995b30573a9b55cfaab80c3293b7c35c1f8/internal-packages/run-engine/src/engine/index.ts#L2801)). **[docs]** "A common pattern we use is to read the current state and check that the passed in `snapshotId` matches the current `snapshotId`. If it doesn't, we know that the state has moved on" (run-engine README).
- **[code]** On a stall, a `PENDING_EXECUTING` run is nacked and requeued; an `EXECUTING` run fails the attempt with `TASK_RUN_STALLED_EXECUTING` and may retry ([T:`engine/index.ts#L2787`](https://github.com/triggerdotdev/trigger.dev/blob/41ad1995b30573a9b55cfaab80c3293b7c35c1f8/internal-packages/run-engine/src/engine/index.ts#L2787)).
- **[code]** The general-purpose redis-worker queue is SQS-like: a single zset per queue scores each item by the time it becomes visible. `dequeueItems` re-scores a taken item to `now + visibilityTimeoutMs` in the same zset ([T:`redis-worker/src/queue.ts#L565`](https://github.com/triggerdotdev/trigger.dev/blob/41ad1995b30573a9b55cfaab80c3293b7c35c1f8/packages/redis-worker/src/queue.ts#L565)), so a crashed worker's item reappears with no separate reaper. Ack and requeue are fenced by a per-enqueue `deduplicationKey`: an attempt whose item was replaced by a newer enqueue is left alone ([T:`queue.ts#L672`](https://github.com/triggerdotdev/trigger.dev/blob/41ad1995b30573a9b55cfaab80c3293b7c35c1f8/packages/redis-worker/src/queue.ts#L672)). `now` is the client's `Date.now()`.
- **[code]** The newer FairQueue in redis-worker moves claimed messages into an in-flight zset scored by deadline; `heartbeat` re-scores it to `Date.now() + extendMs` and `reclaimTimedOut` returns expired ones, 100 per pass ([T:`fair-queue/visibility.ts#L235`](https://github.com/triggerdotdev/trigger.dev/blob/41ad1995b30573a9b55cfaab80c3293b7c35c1f8/packages/redis-worker/src/fair-queue/visibility.ts#L235), [T:`#L397`](https://github.com/triggerdotdev/trigger.dev/blob/41ad1995b30573a9b55cfaab80c3293b7c35c1f8/packages/redis-worker/src/fair-queue/visibility.ts#L397)). The in-flight member is `messageId:queueId`, with no per-claim token, so a heartbeat from a consumer whose claim was reclaimed and re-claimed would extend the new claim.

### 2.3 Reconcilers built after the fact

- **[docs]** "v4 gets a current concurrency sweeper to ensure runs that have finished aren't, for whatever reason, stuck in the current concurrency set of the environment/queue, causing degraded concurrency." A mark phase finds runs in the sets that completed more than 5 minutes ago; a sweep phase acks them ([PR #2206](https://github.com/triggerdotdev/trigger.dev/pull/2206), 2025-06-30). **[code]** The scan runs every 10 minutes over all concurrency sets and calls back into the engine, which queries Postgres ([T:`run-queue/index.ts#L4953`](https://github.com/triggerdotdev/trigger.dev/blob/41ad1995b30573a9b55cfaab80c3293b7c35c1f8/internal-packages/run-engine/src/run-queue/index.ts#L4953)).
- **[code]** The dequeue script now also runs "the bounded reconcile once (heals leaked members)" when a total-concurrency gate is saturated ([T:`#L6311`](https://github.com/triggerdotdev/trigger.dev/blob/41ad1995b30573a9b55cfaab80c3293b7c35c1f8/internal-packages/run-engine/src/run-queue/index.ts#L6311)).
- **[docs]** The sweeper itself left tombstones: it acked runs without removing them from the worker list, so a later `BLPOP` returned a message key that no longer existed ([PR #3527](https://github.com/triggerdotdev/trigger.dev/pull/3527), opened 2026-05, unmerged at the time of reading).

### 2.4 Incidents

- **[docs]** September 2025: "Engine crashes caused some runs to be removed from Redis without being moved to `PENDING_EXECUTING` in Postgres"; they "were no longer queued and never started". A new queue monitor "detects inconsistencies between Redis and Postgres" and "can requeue affected runs and correct concurrency limits", still run by hand at the time. The engine crashed because errors over 1.4 MB were not offloaded like outputs, and `batchTriggerAndWait()` fetched about 700 MB per batch; errors are now trimmed to 16 kB. One master-queue shard grew so large that, with a cap on keys read per pass, "some queues were never evaluated" ([Incident report, Sep 26 2025](https://trigger.dev/blog/incident-report-sep-26-2025)).
- **[docs]** May 2024: completion messages for some v3 runs failed to reach the platform under database load, so the UI showed them executing after they had finished; over-limit runs were retried in a loop until they were rescheduled after a delay, because "it was thrashing the database with the same runs" ([Incident report, May 10 2024](https://trigger.dev/blog/incident-report-may-10-2024)).

### 2.5 Fairness

- **[code]** The run queue's `FairQueueSelectionStrategy` shuffles environments with optional biases toward higher limits and spare capacity, and orders queues inside an environment by age, with a `queueAgeRandomization` knob that defaults to 0, strict oldest first ([T:`fairQueueSelectionStrategy.ts#L38`](https://github.com/triggerdotdev/trigger.dev/blob/41ad1995b30573a9b55cfaab80c3293b7c35c1f8/internal-packages/run-engine/src/run-queue/fairQueueSelectionStrategy.ts#L38)).
- **[code]** FairQueue offers pluggable schedulers, among them Deficit Round Robin with atomic deficit updates in Lua and a cap on deficit ([T:`fair-queue/schedulers/drr.ts#L14`](https://github.com/triggerdotdev/trigger.dev/blob/41ad1995b30573a9b55cfaab80c3293b7c35c1f8/packages/redis-worker/src/fair-queue/schedulers/drr.ts#L14)).

### 2.6 Wake-up, delays, clocks, lost replies

- **[code]** Workers block on `BLPOP` with a 10 s default timeout, on a duplicated connection. After an ack or nack, the next move into the worker list is an `enqueueOnce` job deduplicated per queue, 500 ms later ([T:`run-queue/index.ts#L2602`](https://github.com/triggerdotdev/trigger.dev/blob/41ad1995b30573a9b55cfaab80c3293b7c35c1f8/internal-packages/run-engine/src/run-queue/index.ts#L2602)).
- **[docs]** A delayed run is held in the `DELAYED` state by a redis-worker job and enqueued after the delay (run-engine README diagram).
- **[code]** Scripts mostly take time as an argument (`String(Date.now())`); a few, for TTL expiry and the dead-letter queue, call `TIME`.
- **[code]** redis-worker creates its ioredis client with `maxRetriesPerRequest: 20` ([T:`redis-worker/src/queue.ts#L71`](https://github.com/triggerdotdev/trigger.dev/blob/41ad1995b30573a9b55cfaab80c3293b7c35c1f8/packages/redis-worker/src/queue.ts#L71)), so ioredis can resend its non-idempotent scripts after a reconnect.

## 3. Against the prototype

| Concern                | Inngest                                                                      | Trigger.dev                                                  | Prototype (`prototype/run-engine`)                                           |
| ---------------------- | ---------------------------------------------------------------------------- | ------------------------------------------------------------ | ---------------------------------------------------------------------------- |
| Time source            | Worker clock, in the ULID                                                    | `Date.now()` as argument, `TIME` in a few scripts            | Redis `TIME` in Lua                                                          |
| Lease                  | 30 s, renewed every 15 s, rotating ULID                                      | none in Redis; 60 s heartbeat on a Postgres snapshot         | executing zset scored by `TIME` plus the lease, one batched renewal per tick |
| Fencing token          | lease ULID (renewal only), generation (lease only), step-ID first write wins | snapshot ID on every engine call, under Redlock              | epoch on every write and read                                                |
| Lost reply             | client does not resend writes; lease expiry recovers                         | ioredis resends; no idempotency                              | idempotent fetch (token) and settle (`ended:<epoch>`)                        |
| Concurrency slot       | separate permit with its own lease; deadlock fixed in PR #5132               | separate sets; sweeper plus in-Lua reconcile                 | lives and dies with the lease                                                |
| Hand-off to the worker | lease is one script                                                          | Lua move, `RPUSH`, `BLPOP`, `GET`: stranded runs in Sep 2025 | fetch in one script                                                          |
| Reaper                 | one elected scavenger, 30 s, 100 per pass, random offset, `ScavengeCount`    | concurrency sweeper (10 min), queue monitor                  | expiry read from the executing zset                                          |
| Wake-up                | 10 ms poll                                                                   | `BLPOP` outside Lua, debounced moves                         | marker zset plus `BZPOPMIN`, fetch in Lua                                    |
| Delays                 | future score in the ready zset                                               | delayed job, then enqueue                                    | one pending zset                                                             |
| Retention              | item deleted on dequeue, 12 h tombstone; history in ClickHouse               | message deleted on ack; history in Postgres                  | to be designed                                                               |

## 4. What an own nextasking engine could copy or avoid

Facts above, framed as options for the design ticket.

Copy:

1. **Tie the concurrency slot to the lease** (the prototype already does). Both projects that split them built reconcilers, and Inngest still hit a deadlock.
2. **Hand the lease to the worker in one script**, never through a list pop outside Lua: Trigger.dev's split hand-off is what stranded runs in September 2025.
3. **Fence with a token that changes on every hand-over and check it on every write**, not only on renewal. Inngest had to add a generation counter late; Trigger.dev checks the snapshot ID everywhere.
4. **Stop the attempt locally when the lease expires before a renewal succeeds**, as Inngest does for its capacity lease, rather than wait for the renewal's reply.
5. **Enqueue idempotently with a deterministic ID and a tombstone that outlives the job** (Inngest: item check plus a 12 h `seen` key on dequeue).
6. **Bound the reaper**: one holder at a time, a batch limit, a random start in a large backlog, dropping index entries whose record is gone, and a per-run count of reaps (Inngest's `ScavengeCount`, which matches the stall rule).
7. **Keep every "due at" in one sorted set and one clock**, as both do for delays; redis-worker shows a single "visible at" zset can also absorb lease expiry.
8. **Use one hash tag and scale by separate instances**, not slots (Inngest's queue shards).
9. **Cap stored error and output sizes** (Trigger.dev trims errors to 16 kB after a 700 MB fetch crashed the engine).
10. **Favor continuing runs over starting new ones when picking work** (Inngest weights continuation backlogs ten to one).

Avoid:

1. **Concurrency counters or sets updated apart from the run's state**: they leak (Trigger.dev #2206, #3527; Inngest #5132).
2. **A queue per concurrency key at high cardinality**: Inngest's key queues made each queue cost four times an item and throughput fell.
3. **The client's clock for lease expiry**: both rely on it and pay with long leases; the prototype's `TIME` is safer.
4. **Unbounded memory in Redis**: Inngest's main reason to leave Valkey is that "running out of memory takes the whole cluster down". Retention needs hard bounds and `noeviction`.
5. **Promising more durability than Redis gives**: Inngest says unpersisted writes are lost on a hard failure; fencing keeps the engine safe, but an acked dispatch can still vanish.
6. **Pure polling at a short interval** (Inngest, 10 ms) for a library that shares the app's Redis: it is constant load with no work; a blocking wake-up is cheaper when idle.

## 5. Surprises

- Inngest, the reference "own Redis queue", is moving that queue off Redis (Valkey) to FoundationDB in 2026, citing memory, durability and single-thread fairness limits.
- Neither project fences queue writes the way the prototype does: Inngest's requeue and dequeue trust the caller, and Trigger.dev keeps all fencing in Postgres.
- Neither uses Redis `TIME` for leases.
- Trigger.dev's run queue has no lease at all; the reaper is a delayed job per run that each heartbeat pushes back.
