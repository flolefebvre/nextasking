# Redis and Valkey behaviour an own engine relies on

Research for [#125](https://github.com/flolefebvre/nextasking/issues/125), a child of the map [#123](https://github.com/flolefebvre/nextasking/issues/123). The question: what Redis 7/8 and Valkey 8/9 guarantee for an engine built on Lua scripts. It covers script atomicity and effects replication; what a failover loses and what `WAIT` changes; `BZPOPMIN` and blocked clients across a failover or a reconnect; `TIME` inside scripts; the script cache and `NOSCRIPT`; the Redis/Valkey differences that matter; Cluster limits with one hash tag; and memory per run at 10k and 100k runs for the prototype's layout. These are facts and measurements. The design decisions belong to the tickets this one blocks.

The prototype is branch [`prototype/run-engine`](https://github.com/flolefebvre/nextasking/tree/prototype/run-engine), commit read on 2026-11-08. Below, `proto:` links are relative to `https://github.com/flolefebvre/nextasking/blob/prototype/run-engine/src/prototype-run-engine/`.

## Summary

1. **A script is isolated, not transactional.** Nothing interleaves with it, but a runtime error after a write keeps the writes made before it. All four servers kept a `SET` made before a failing `INCR`. The engine has to check every precondition before its first write. The prototype's `settle.lua` does not ([§1](#1-atomicity-isolation-without-rollback)).
2. **Only the effects are replicated** (the only mode since Redis 7.0; Valkey inherits it). Replicas and the AOF receive the script's writes wrapped in `MULTI`/`EXEC`, so `TIME` and random values are safe in scripts that write ([§2](#2-effects-replication)).
3. **`TIME` in a script is frozen at the script's start, and it is the wall clock.** Two `TIME` calls 50 ms apart in one script returned the same value on all four servers. The source is `gettimeofday`, which is not monotonic. A clock step on the primary, or skew between the old and the promoted primary, moves every lease and due time ([§3](#3-time-inside-scripts)).
4. **A failover can lose acknowledged writes, and `WAIT` only narrows that window.** Both projects document this. `WAIT` inside a script does not block. **The prototype's per-attempt epoch is not unique across such a failover.** Reproduced on Valkey 9 and Redis 8: the promoted replica gave out epoch 1 again, the stale attempt's `save-step` and `settle` were accepted, and the live attempt's `settle` returned `already` ([§4](#4-failover-and-wait)).
5. **`BZPOPMIN` is a wake-up hint, never state.** Blocked clients are served in FIFO order, after the script that wrote the key ends. Inside a script the command returns nil at once. On a primary→replica switch, blocked clients get `-UNBLOCKED` and are disconnected (Valkey 9 can redirect them instead). A pop whose reply is lost consumes the marker, and ioredis resends the `BZPOPMIN`, which then waits out its timeout. The prototype's 1 s timeout plus a fetch after every wake keeps that harmless ([§5](#5-bzpopmin-and-blocked-clients)).
6. **The script cache is volatile, and since Redis 7.4 and Valkey 8.0 it also evicts.** Restart, failover and `SCRIPT FLUSH` empty it. On top of that, scripts first seen through `EVAL` are capped at 500, oldest evicted first. The docs on both sides are silent on the cap; the source has it. ioredis loads every script through `EVAL` and retries a `NOSCRIPT` once, so `NOSCRIPT` is safe: a script that returns it did not run ([§6](#6-script-cache-and-noscript)).
7. **Low memory never splits a script.** Under `maxmemory`, a script is refused only at its first write that can grow memory, before anything is written. A script whose first write is `ZPOPMIN`, `HDEL` or `ZREM` runs to the end, past the limit. A `#!lua` shebang makes the refusal happen up front for every script. `noeviction` is the default on all four images ([§7](#7-low-memory-and-slow-scripts)).
8. **On Cluster, the prototype's scripts fail as written.** It declares no keys (`numberOfKeys: 0`). ioredis Cluster sends such a command to a random node, and the server refuses a script that touches a key it does not own. The scripts need at least one declared key under the hash tag. Undeclared keys in the same slot work, except during a legacy slot migration. One hash tag means one slot on one primary: Cluster then adds failover, not capacity ([§8](#8-cluster-with-one-hash-tag)).
9. **Valkey and Redis run the same scripting code paths.** Four differences matter. Valkey reports `redis_version:7.2.4` (and `redis.REDIS_VERSION` 7.2.4 in Lua). Hash-field expiry exists only on Redis ≥ 7.4 and Valkey ≥ 9.0, so not on the Valkey 8 that CI tests. Valkey 9 migrates whole slots atomically. Valkey 9 redirects blocked clients after a failover ([§9](#9-redis-and-valkey-differences-that-matter)).
10. **Memory, measured with the prototype's own scripts.** A pending run takes about 0.5 KB. A completed run with three small steps takes 0.9 KB. With a 200 B payload and three 120 B steps it takes 1.9 to 2.2 KB, because any hash value over 64 bytes switches the whole hash from listpack to hashtable. Each extra zset index costs 100 to 130 B per run. So 10k runs take 5 to 22 MB, and 100k runs take 50 to 220 MB ([§10](#10-memory-per-run)).

## 1. Atomicity: isolation without rollback

- **What the docs promise.** "Redis guarantees the script's atomic execution. While executing the script, all server activities are blocked during its entire runtime. These semantics mean that all of the script's effects either have yet to happen or had already happened." ([redis.io: Scripting with Lua](https://redis.io/docs/latest/develop/programmability/eval-intro/)). Valkey's page says the same ([valkey.io: eval-intro](https://valkey.io/topics/eval-intro/)). That is a promise about what other clients can see, not about rolling back.
- **What happens on an error.** `redis.call()` raises a runtime error back to the client ([redis.io: Lua API, redis.call](https://redis.io/docs/latest/develop/programmability/lua-api/#redis.call)). Writes already made stay. Neither docs page says so outright, so it was measured: `EVAL "redis.call('SET', KEYS[1], 'written'); redis.call('INCR', KEYS[2]); ..." 2 c b`, with `b` holding a non-number, returned `ERR value is not an integer` and left `c = written` on Valkey 8.1.11, Valkey 9.1.3, Redis 7.4.12 and Redis 8.10.3. Returning `redis.error_reply(...)` after a write works the same way: the error goes to the client and the writes stay.
- **For the engine.** Each script reads and checks everything first, then writes, and never raises an error once it has written. **The prototype's `settle.lua` breaks this rule.** It calls `end_lease` (`ZREM executing`, `HSET ended:<epoch>`, `HDEL leaseUntil`, releasing the slot and waking a parked run) on [line 11](https://github.com/flolefebvre/nextasking/blob/prototype/run-engine/src/prototype-run-engine/prototype-lua/settle.lua#L11), and only rejects an unknown kind on [line 25](https://github.com/flolefebvre/nextasking/blob/prototype/run-engine/src/prototype-run-engine/prototype-lua/settle.lua#L25). An unknown kind therefore leaves a run whose state field says `executing` but which is in no index. Nothing will ever pick it up again.
- **Slow scripts.** The default limit is 5 s (`busy-reply-threshold`). Past it, the server answers `BUSY` to everyone. `SCRIPT KILL` works only if the script has not written yet; after a write, `SHUTDOWN NOSAVE` is the only way out ([redis.io: Maximum execution time](https://redis.io/docs/latest/develop/programmability/#maximum-execution-time)). For the engine, every loop needs a fixed bound. The prototype's (50 pops in `fetch`, 200 + 200 in `promote-due`) are such bounds.

## 2. Effects replication

- "In Redis 5.0, effects replication became the default mode. As of Redis 7.0, verbatim replication is no longer supported." The script's write commands "are wrapped into a `MULTI`/`EXEC` transaction and are sent to the replicas and AOF". With effects replication, "you can, for example, use the `TIME` or `SRANDMEMBER` commands inside your scripts freely at any place" ([redis.io: Script replication](https://redis.io/docs/latest/develop/programmability/eval-intro/#script-replication)). `redis.replicate_commands()` is a no-op from 7.0 on ([Lua API](https://redis.io/docs/latest/develop/programmability/lua-api/#redis.replicate_commands)). Valkey forked from Redis 7.2.4 and kept this ([Valkey 8.0 release notes](https://github.com/valkey-io/valkey/blob/8.0/00-RELEASENOTES): "fully compatible with Redis OSS 7.2.4").
- **For the engine.** A replica applies a whole transition or none of it, so a promoted replica never holds half a script. It can, however, lack the last few whole scripts ([§4](#4-failover-and-wait)). Values computed in the script, such as `now + lease`, reach the replica as literals, so the replica's own clock plays no part.

## 3. `TIME` inside scripts

- **Frozen for the whole script.** `TIME` returns the cached `server.ustime` ([redis: server.c#L4879-L4883](https://github.com/redis/redis/blob/8.2/src/server.c#L4879-L4883), [valkey: server.c#L4927-L4931](https://github.com/valkey-io/valkey/blob/9.0/src/server.c#L4927-L4931)). That cache is refreshed only when the outermost execution unit starts (`enterExecutionUnit`, [redis: server.c#L1290-L1299](https://github.com/redis/redis/blob/8.2/src/server.c#L1290-L1299), [valkey: server.c#L1352-L1366](https://github.com/valkey-io/valkey/blob/9.0/src/server.c#L1352-L1366)). The replication page states the same for expiry: "As a Lua script runs, conceptually the time in the master is frozen" ([redis.io: replication and expires](https://redis.io/docs/latest/operate/oss_and_stack/management/replication/#how-redis-replication-deals-with-expires-on-keys)). Measured: two `TIME` calls separated by a 50 ms `os.clock()` spin returned identical values on all four servers.
- **It is the wall clock.** The cache is filled by `ustime()`, which calls `gettimeofday` ([redis: server.c#L227-L235](https://github.com/redis/redis/blob/8.2/src/server.c#L227-L235)). It is not monotonic. `os.clock()` (Redis 7.4, Valkey 8.0) is CPU time for measuring how long a script has run, not a clock ([Lua API: os library](https://redis.io/docs/latest/develop/programmability/lua-api/#os-library), [Valkey 8.0 notes](https://github.com/valkey-io/valkey/blob/8.0/00-RELEASENOTES)).
- **For the engine.** One `now` per script is free and consistent across the script, which is what the prototype's `now_ms()` assumes. "One clock" means the clock of whichever node is primary. An NTP step on it, or skew between the old and the promoted primary, shifts every lease and due time by that amount. If it jumps forward, all leases expire at once (a stall per running run). If it jumps back, leases and sleeps last longer.

## 4. Failover and `WAIT`

- **Acknowledged writes can be lost.** "Redis uses asynchronous replication ... acknowledged writes can still be lost during a failover" ([redis.io: replication](https://redis.io/docs/latest/operate/oss_and_stack/management/replication/)). On Cluster: "A write may reach a master, but while the master may be able to reply to the client, the write may not be propagated to replicas ... the write is lost forever if the master is unreachable for a long enough period that one of its replicas is promoted" ([redis.io: cluster spec, Write safety](https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/#write-safety)).
- **What `WAIT` changes.** `WAIT n timeout` blocks the connection until `n` replicas acknowledge its earlier writes, and returns the count reached. It "does not make Redis a strongly consistent store ... it is possible to still lose a write synchronously replicated to multiple replicas". Sentinel and Cluster only make a "best-effort attempt to promote the best replica" ([redis.io: WAIT](https://redis.io/docs/latest/commands/wait/); [valkey.io: WAIT](https://valkey.io/commands/wait/) says the same). Nothing is rolled back on a timeout. **Inside a script, `WAIT` does not block** and returns at once ("since Redis 7.0, any context that does not allow blocking, such as inside scripts"). Measured: `EVAL "return redis.call('WAIT', 1, 1000)" 0` returned 0 immediately on all four servers. So `WAIT` has to be a separate command, on the same connection, after the script. `min-replicas-to-write` / `min-replicas-max-lag` bound the window in seconds instead, and refuse writes when too few replicas are in sync ([replication: Allow writes only with N attached replicas](https://redis.io/docs/latest/operate/oss_and_stack/management/replication/#allow-writes-only-with-n-attached-replicas)).
- **A promoted replica starts a new replication ID** ([replication: Replication ID explained](https://redis.io/docs/latest/operate/oss_and_stack/management/replication/#replication-id-explained)). That marks a new history, but scripts cannot easily read it, and it does not tell a client which of its writes survived.
- **What a lossy failover does to the prototype** (reproduced; script in [Experiments](#experiments)). Setup: a primary and a replica. Enqueue `run-x` and `WAIT 1` so the replica has it. Cut the replica off the network. Worker A fetches on the primary (epoch 1, token A). Kill the primary and promote the replica. On Valkey 9.1.3 and Redis 8.10.3 alike:
  - `run-x` on the new primary: `pending`, epoch 0. A's fetch is gone.
  - Worker B fetches: `run-x`, **epoch 1**.
  - A's `save-step` with epoch 1 returns `1` (accepted). A's `settle complete` returns `ok`.
  - B's `settle complete`, the attempt that really holds the lease, returns `already`. The run ends `completed` with A's result, and A's step sits in B's step hash.
  - The epoch comes from `HINCRBY epoch` ([proto: fetch.lua#L39](https://github.com/flolefebvre/nextasking/blob/prototype/run-engine/src/prototype-run-engine/prototype-lua/fetch.lua#L39)). A counter is only as durable as its last write, so a lost increment hands the same fence to two attempts. Running twice is the accepted cost of at-least-once delivery. The problem is that the fence stops telling the two attempts apart. The prototype already sends a random token with every fetch ([proto: prototype-worker.ts#L123](https://github.com/flolefebvre/nextasking/blob/prototype/run-engine/src/prototype-run-engine/prototype-worker.ts#L123)). A value unique by construction, such as that token, fences across failovers where a counter cannot. The attempt number can stay a counter for counting.
- **Other losses, by transition** (these follow from the above and were not separately reproduced):
  - A lost `enqueue` loses the whole run. Only a `WAIT` after the dispatch, or the caller retrying, narrows that.
  - A lost `settle` brings the run back as `executing` under the old lease. `promote-due` reclaims it when the lease expires and counts a stall, so the run executes again.
  - A lost dedup or `firing:` key lets a duplicate in.
  - A lost marker costs at most one `BZPOPMIN` timeout.

## 5. `BZPOPMIN` and blocked clients

- **Who gets woken.** "If multiple clients are blocked for the same key, the first client to be served is the one that has been waiting the longest". Blocked clients are served "_only after_ the execution of the command", that is after the whole script or `MULTI`. A blocking command inside `MULTI` behaves as if its timeout were reached: it returns nil ([redis.io: BLPOP](https://redis.io/docs/latest/commands/blpop/), which [BZPOPMIN](https://redis.io/docs/latest/commands/bzpopmin/) defers to). Measured inside a script: `EVAL "return redis.call('BZPOPMIN', KEYS[1], 5)"` on an empty key returned nil at once on all four servers. The timeout is a double, in seconds. `BZPOPMIN` is a write command (`command_flags: write, blocking, fast`), so a replica refuses it with `READONLY`.
- **When the primary becomes a replica.** Redis sends every blocked client `-UNBLOCKED force unblock from blocking operation, instance state changed (master -> replica?)` and closes the connection ([redis: blocked.c#L283-L312](https://github.com/redis/redis/blob/8.2/src/blocked.c#L283-L312), called from [replication.c#L3278](https://github.com/redis/redis/blob/8.2/src/replication.c#L3278)). Valkey 9 does the same, except in two cases ([valkey: blocked.c#L325-L360](https://github.com/valkey-io/valkey/blob/9.0/src/blocked.c#L325-L360); "Redirect blocked clients after failover (#2329)" in the [9.0 notes](https://github.com/valkey-io/valkey/blob/9.0/00-RELEASENOTES)). In cluster mode it answers `-MOVED`. In standalone mode it answers `-REDIRECT host:port` to clients that declared the `redirect` capability. In cluster mode on both servers, a client blocked on a key whose slot moved away is redirected (`clusterRedirectBlockedClientIfNeeded`, [redis: cluster.c#L1365](https://github.com/redis/redis/blob/8.2/src/cluster.c#L1365), [valkey: cluster.c#L1358](https://github.com/valkey-io/valkey/blob/9.0/src/cluster.c#L1358)).
- **When the connection drops.** ioredis resends every command that got no reply once it reconnects (`autoResendUnfulfilledCommands`, default `true`; [ioredis v5.11.1: event_handler.ts#L340-L356](https://github.com/redis/ioredis/blob/v5.11.1/lib/redis/event_handler.ts#L340-L356)). That includes the `BZPOPMIN`. If the server had already popped the marker when the reply was lost, the marker is gone and the resent pop waits for its full timeout.
- **When the connection hangs.** A half-open TCP connection, for example to a primary that vanished without a RST, leaves `BZPOPMIN` waiting until TCP notices. ioredis 5.11.1 defaults to `keepAlive: 0`, which enables keepalive with the OS's initial delay (7200 s on Linux by default). ioredis 6.0.0 defaults to 30 000 ms ([v5.11.1 RedisOptions.ts#L240](https://github.com/redis/ioredis/blob/v5.11.1/lib/redis/RedisOptions.ts#L240), [v6.0.0 RedisOptions.ts#L297](https://github.com/redis/ioredis/blob/v6.0.0/lib/redis/RedisOptions.ts#L297)). The opt-in `blockingTimeout` option arms a client-side timer of the command's own timeout plus `blockingTimeoutGrace` (100 ms). On expiry it resolves the command with `null`, like a server timeout ([v5.11.1 RedisOptions.ts#L22-L34](https://github.com/redis/ioredis/blob/v5.11.1/lib/redis/RedisOptions.ts#L22-L34), [Redis.ts#L604-L628](https://github.com/redis/ioredis/blob/v5.11.1/lib/Redis.ts#L604-L628), [Command.ts#L391-L413](https://github.com/redis/ioredis/blob/v5.11.1/lib/Command.ts#L391-L413)).
- **For the engine.** Every lost-wake case (a popped marker whose reply was lost, a marker write lost in a failover, an `UNBLOCKED` error) costs at most one timeout, provided the worker fetches after every wake and every timeout, and never blocks with timeout 0. The prototype already does both ([proto: prototype-worker.ts#L113-L142](https://github.com/flolefebvre/nextasking/blob/prototype/run-engine/src/prototype-run-engine/prototype-worker.ts#L113-L142)). Setting `blockingTimeout` on the blocking connection closes the half-open case. The one-member marker wakes one worker per arm, and `fetch` re-arms it while work remains, so the wake-ups chain from worker to worker.

## 6. Script cache and `NOSCRIPT`

- **Volatile by design.** "The Redis script cache is **always volatile**. It isn't considered as a part of the database and is **not persisted**. The cache may be cleared when the server restarts, during fail-over when a replica assumes the master role, or explicitly by `SCRIPT FLUSH`" ([redis.io: Cache volatility](https://redis.io/docs/latest/develop/programmability/eval-intro/#cache-volatility); [valkey.io](https://valkey.io/topics/eval-intro/) has the same wording). `NOSCRIPT` means the script did not run, so resending it is always safe.
- **Evicted when too many.** Neither docs page says so, but since Redis 7.4 ("#13108 Lua: LRU eviction for scripts generated with `EVAL` \*\*\* BEHAVIOR CHANGE \*\*\*", [7.4 release notes](https://github.com/redis/redis/blob/7.4/00-RELEASENOTES)) scripts first seen through `EVAL` are capped at 500, oldest evicted first (`LRU_LIST_LENGTH 500`, [redis: eval.c#L534-L550](https://github.com/redis/redis/blob/8.2/src/eval.c#L534-L550); [valkey: eval.c#L351-L362, L459-L462](https://github.com/valkey-io/valkey/blob/9.0/src/eval.c#L351-L362)). Valkey has had it since 8.0 (its 8.0 notes fix "a crash ... when scripts are evicted from the script cache (#1310)"). Scripts loaded with `SCRIPT LOAD` are exempt. `INFO` counts evictions as `evicted_scripts`. So on a server shared with an app that sends many distinct `EVAL` scripts, `NOSCRIPT` can come at any time, not only after a restart.
- **What ioredis does.** On the first call per socket, `defineCommand` sends `EVAL` with the full source, and `EVALSHA` after that. On `NOSCRIPT` it forgets that the socket has the script and resends once, which becomes an `EVAL`. In a pipeline, that resend goes outside the pipeline ([ioredis v5.11.1: Script.ts](https://github.com/redis/ioredis/blob/v5.11.1/lib/Script.ts); unchanged in v6.0.0). Because every script is loaded through `EVAL`, the engine's scripts are subject to the 500 cap. The ioredis docs only say it "will try to use `EVALSHA` internally when possible" ([ctx7 /redis/ioredis](https://github.com/redis/ioredis/blob/main/README.md)).
- **Functions (`FUNCTION LOAD`)** are persisted and replicated, so they survive restarts and failovers ([redis.io: programmability](https://redis.io/docs/latest/develop/programmability/)). In exchange they are named server-side state shared by every client. Judgement, not measured: during a rolling deploy, two library versions sharing a Redis would replace each other's library, whereas content-addressed `EVALSHA` lets the two versions coexist.

## 7. Low memory and slow scripts

- **Where the check happens.** "the first write command encountered in the script that uses additional memory will cause the script to abort ... an exception ... is when the script's first write command does not use additional memory, as is the case with ... `DEL` and `LREM`. In this case, Redis will allow all commands in the script to run to ensure atomicity" ([redis.io: Execution under low memory conditions](https://redis.io/docs/latest/develop/programmability/eval-intro/#execution-under-low-memory-conditions)). The source applies the check only while the script "had no side effects so far" (`!(run_ctx->flags & SCRIPT_WRITE_DIRTY)`, [redis: script.c#L452-L474](https://github.com/redis/redis/blob/8.2/src/script.c#L452-L474)). With a `#!lua` shebang, a script is "denied ... when in an OOM state" before it runs, unless it carries `allow-oom` ([Lua API: script flags](https://redis.io/docs/latest/develop/programmability/lua-api/#script_flags)).
- **Measured** with `maxmemory 1` and the script `HDEL` then `SET`. Without a shebang it ran and wrote its key. With `#!lua` it returned `OOM command not allowed`. Same on all four servers.
- **For the engine.** OOM never splits a transition. Without a shebang, transitions that start with `ZPOPMIN`, `ZREM` or `HDEL` (most of the prototype's) keep running past `maxmemory`, while one that starts with `HSET` is refused. A `#!lua` line on every script makes the refusal uniform and up front. A shebang also forbids cross-slot keys, which one hash tag never uses, and it still allows undeclared keys in the same slot (measured on all four). `noeviction` is the default `maxmemory-policy` on all four images (`CONFIG GET`), which is what the existing worker boot check requires.

## 8. Cluster with one hash tag

- **Declared keys route the script.** "all names of keys that a script accesses must be explicitly provided as input key arguments" ([eval-intro](https://redis.io/docs/latest/develop/programmability/eval-intro/#script-parameterization); [valkey.io](https://valkey.io/topics/eval-intro/) says the same). ioredis Cluster takes the slot from the command's first key. A script with no keys gets no slot and goes to a random node (`getSlot`, [ioredis v5.11.1: Command.ts#L275-L285](https://github.com/redis/ioredis/blob/v5.11.1/lib/Command.ts#L275-L285); `getSampleInstance`, [cluster/index.ts#L629-L667](https://github.com/redis/ioredis/blob/v5.11.1/lib/cluster/index.ts#L629-L667); same in v6.0.0). On a node that does not own the slot, the script's first key access fails with `Script attempted to access a non local key in a cluster node`. That is a script error, not a `MOVED`, so ioredis does not follow it ([redis: script.c#L476-L516](https://github.com/redis/redis/blob/8.2/src/script.c#L476-L516), [valkey: script.c#L423-L462](https://github.com/valkey-io/valkey/blob/9.0/src/script.c#L423-L462)). **The prototype defines every script with `numberOfKeys: 0`** ([proto: prototype-run-engine.ts#L80](https://github.com/flolefebvre/nextasking/blob/prototype/run-engine/src/prototype-run-engine/prototype-run-engine.ts#L80)) and builds every key name from a prefix in `ARGV`, so on Cluster it works only on the nodes that happen to own the slot. Declaring one fixed key under the tag (for example `{nextasking}:marker`) as `KEYS[1]` fixes the routing.
- **Undeclared keys still work, with one exception.** The prototype has to touch keys it cannot declare up front, such as a woken parked run or due runs, and accessing undeclared keys in the same slot is allowed. The exception is a legacy (key-by-key) slot migration: while the slot is migrating, a script touching undeclared keys fails with `Unable to execute command ... because undeclared keys were accessed during rehashing of the slot` (same source lines). Ordinary multi-key commands then get `-TRYAGAIN` ([cluster spec: Multi-keys operations](https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/#multi-keys-operations)). Both errors are raised before the command runs. Valkey 9's atomic slot migration moves a whole slot at once, and "the original node still retains all the keys and data until the entire slot migration is complete" ([valkey.io: Introducing Valkey 9](https://valkey.io/blog/introducing-valkey-9/)). The TRYAGAIN/"unstable" checks key off the legacy `MIGRATING`/`IMPORTING` slot state ([valkey: cluster.c#L1103-L1113](https://github.com/valkey-io/valkey/blob/9.0/src/cluster.c#L1103-L1113)). Inference, not tested: the window does not exist under atomic migration.
- **Hash tag rules.** Only the substring between the first `{` and the next `}` is hashed, and it must not be empty ([cluster spec: Hash tags](https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/#hash-tags)). So `{nextasking}:` puts every key in one slot.
- **What one slot costs.** A slot is served by exactly one primary at a time, so all of nextasking's keys, memory and command CPU sit on one shard. Adding shards adds nothing; Cluster then adds failover, not capacity. Moving that one slot (resharding) moves everything at once. Valkey 8's `CLUSTER SLOT-STATS` shows the per-slot load ([Valkey 8.0 notes](https://github.com/valkey-io/valkey/blob/8.0/00-RELEASENOTES)). Valkey 9 allows numbered databases in cluster mode; Redis Cluster supports only database 0.

## 9. Redis and Valkey differences that matter

- **The scripting code is the same.** The OOM check, the cluster key checks, the frozen `TIME`, the `EVAL` LRU of 500 and the blocked-client handling are the same functions with the same logic in both trees (links above). Every experiment above gave the same result on all four servers.
- **Version detection.** Valkey reports `redis_version:7.2.4` and, in Lua, `redis.REDIS_VERSION` = `7.2.4`, whatever its real version. Measured on 8.1.11 and 9.1.3. Its own version is in `valkey_version` and `server_name:valkey` in `INFO server`. Any feature check has to read those, not `redis_version`.
- **Hash-field expiry** (`HEXPIRE`, `HSETEX`, ...) exists on Redis since 7.4 and on Valkey only since 9.0 ([Introducing Valkey 9](https://valkey.io/blog/introducing-valkey-9/)). It is missing on the `valkey/valkey:8` that CI tests ([ci.yml matrix](https://github.com/flolefebvre/nextasking/blob/main/.github/workflows/ci.yml)), so retention cannot use it while Valkey 8 is supported. Redis 8's `HGETDEL` is not in Valkey 9's list.
- **Blocked clients on failover.** Valkey 9 redirects them (`-MOVED`, or `-REDIRECT` with the `redirect` capability); Redis disconnects them with `-UNBLOCKED`. ioredis does not opt into `redirect`, so in standalone mode both behave the same for this engine.
- **Slot migration.** Valkey 9 migrates whole slots atomically; Redis migrates key by key ([§8](#8-cluster-with-one-hash-tag)).
- **Memory per run.** Within 10 % of each other ([§10](#10-memory-per-run)).

## 10. Memory per run

Measured on 2026-11-08 by driving the prototype's own `enqueue`, `fetch`, `save-step` and `settle` scripts (lib + script, exactly as `RunEngine` concatenates them) through `--pipe`, against one throwaway container per image started with `--save "" --appendonly no`. The method:

- Each figure is `used_memory` after the runs minus `used_memory` after `FLUSHALL SYNC` + `SCRIPT FLUSH`, minus the growth of `used_memory_scripts_eval`.
- The 60 s `fetch:<token>` keys are deleted before measuring.
- Run ids are 36-character UUID strings, the prefix is `{nextasking}:`, the task name is `send-welcome-email`, and there is no concurrency scope.
- `used_memory` is what the allocator was asked for. RSS adds fragmentation on top.

Bytes per run, at 100k runs (10k in brackets):

| Layout                                                                    | Valkey 8.1.11 | Valkey 9.1.3  | Redis 7.4.12  | Redis 8.10.3  |
| ------------------------------------------------------------------------- | ------------- | ------------- | ------------- | ------------- |
| Pending: run hash (64 B payload) + `pending` zset                         | 512 (540)     | 512 (539)     | 555 (595)     | 521 (557)     |
| Completed: 40 B payload, 3 steps × 40 B, 40 B result, `completed` zset    | 878 (911)     | 877 (911)     | 946 (967)     | 892 (910)     |
| Completed: 200 B payload, 3 steps × 120 B, 120 B result, `completed` zset | 1 950 (1 961) | 1 981 (1 992) | 2 211 (2 210) | 1 884 (1 882) |
| One more zset index (UUID member, ms score)                               | 99 (100)      | 98 (100)      | 120 (134)     | 106 (115)     |

Totals: 10k completed runs take 9 to 22 MB, and 100k take 88 to 221 MB, plus about 10 to 12 MB per 100k runs for each extra index the read API adds (by task, by creation time, and so on).

- **The 64-byte cliff.** `hash-max-listpack-value` is 64 on all four (`hash-max-listpack-entries` 512). One value longer than 64 bytes turns the whole hash into a hashtable. `MEMORY USAGE` of the same run hash on Valkey 9 went from 464 B (listpack) to 1 136 B (hashtable) when the payload grew by 160 B and the result by 80 B. That is about 430 B of encoding overhead per hash, and the step hash pays it too (272 B to 688 B). Keeping payloads, results and step values out of the record hash, or the record's fields short, keeps the record in listpack form. A separate string key per blob has its own per-key cost, which was not measured here.
- **What grows that the table leaves out.** The table shows a run that succeeded on its first attempt. Each further attempt adds an `ended:<epoch>` field (with a UUID fence, about 45 B of field name, still under 64). Each fetch leaves a `fetch:<token>` string for 60 s. Completed and failed runs stay until retention removes them.

## Experiments

All run on 2026-11-08 against `valkey/valkey:8` (8.1.11), `valkey/valkey:9` (9.1.3), `redis:7.4` (7.4.12) and `redis:8` (8.10.3), each a fresh container with `--save "" --appendonly no`. The scripts were throwaway and are not committed. What each did:

- **Partial write.** `SET b notanumber`, then `EVAL "redis.call('SET', KEYS[1], 'written'); redis.call('INCR', KEYS[2]); return 'unreached'" 2 c b`. Result: error, and `GET c` returned `written` on all four.
- **Frozen `TIME`.** `EVAL "local a = redis.call('TIME'); local t = os.clock(); while os.clock() - t < 0.05 do end; local b = redis.call('TIME'); return {a[1]..'.'..a[2], b[1]..'.'..b[2]}" 0`. The two values were identical on all four.
- **`WAIT` and `BZPOPMIN` in a script.** `WAIT 1 1000` returned 0 at once (no replica). `BZPOPMIN empty 5` returned nil at once.
- **OOM.** `CONFIG SET maxmemory 1`. Then `HDEL` + `SET` without a shebang: ran and wrote. The same with `#!lua`: `OOM command not allowed`. A `#!lua` script with one declared key and an undeclared key under the same tag worked.
- **Lossy failover.** Done on Valkey 9.1.3 and Redis 8.10.3, with the prototype's own `enqueue`, `fetch`, `save-step` and `settle` scripts:
  1. Two containers on a user network, the second started with `--replicaof`.
  2. Wait for `master_link_status:up`.
  3. `enqueue run-x`, then `WAIT 1 1000`, which returned 1.
  4. `docker network disconnect` the replica, then `fetch token-a` on the primary, which returned epoch 1.
  5. `docker kill` the primary, reconnect the replica, `REPLICAOF NO ONE`.
  6. Then the `fetch`/`save-step`/`settle` sequence shown in [§4](#4-failover-and-wait).

  `docker pause` on the replica was tried first and did _not_ lose the write: the replication stream waited in the paused container's socket buffer and was applied on unpause.

- **Memory.** As described in [§10](#10-memory-per-run).

## For the prototype

Each item is cited in its section above.

- Fence attempts with a value unique by construction (the fetch token), not with an `HINCRBY` counter. A lossy failover reissues the counter's value ([§4](#4-failover-and-wait)).
- Declare at least one key under the hash tag as `KEYS[1]` in every script, or none of them will route on Cluster ([§8](#8-cluster-with-one-hash-tag)).
- In `settle.lua`, validate the transition kind before `end_lease` writes anything ([§1](#1-atomicity-isolation-without-rollback)).
- Keep the finite `BZPOPMIN` timeout and the fetch after every wake. Add ioredis `blockingTimeout` on the blocking connection ([§5](#5-bzpopmin-and-blocked-clients)).
- Consider `#!lua` on every script so that OOM is refused before any write ([§7](#7-low-memory-and-slow-scripts)).
- Keep blobs (payload, result, step values) from pushing the run hash past the 64-byte listpack limit, or budget about 2 KB per run ([§10](#10-memory-per-run)).
- Do not use hash-field expiry while Valkey 8 is supported. Detect Valkey through `valkey_version`, not `redis_version` ([§9](#9-redis-and-valkey-differences-that-matter)).
