# Testing

- The suite runs on Vitest 5 (`vitest.config.ts`) as three projects: `unit` (`pnpm test:unit`), which never needs Docker, `integration` (`pnpm test:integration`), which runs against a real server, and `e2e` (`pnpm test:e2e`), which runs the packed package in a Next app. `pnpm test` and `pnpm check` run `unit` and `integration`, so they need Docker unless `NEXTASKING_TEST_REDIS_URL` is set; `pnpm gate` runs all three, `e2e` last.
- Name a test file after its project: `foo.test.ts` is a unit test, `foo.integration.test.ts` an integration test, `foo.e2e.test.ts` an e2e test. The suffix alone decides the project.
- Collocate a test with the file it tests (`foo.test.ts` or `foo.integration.test.ts` next to `foo.ts`) under `src/`; `tsconfig.build.json` keeps them out of `dist`.
- Put a scenario that crosses modules or processes in `tests/` instead, named as a sentence saying what it proves (`tests/a-server-round-trips-a-value.integration.test.ts`). The shared harness lives there too, named after what it exports.
- Lay out each test body as Arrange / Act / Assert, one blank line between phases; two phases that fuse into one statement share a block, and a phase a test doesn't have is simply absent.

## Integration harness

- `tests/global-setup.ts` starts one container per run with testcontainers and discards it at teardown; every integration test talks to that server.
- The image is `valkey/valkey:9` unless `NEXTASKING_TEST_IMAGE` names another; CI runs the `test` job once per image in its matrix (`docs/codebase/ci.md`).
- Set `NEXTASKING_TEST_REDIS_URL` to a full URL (credentials, port, `rediss:` included) to run against a server already running instead; no container starts then. An empty variable counts as unset, for both.
- Write an integration test with `integrationTest` from `tests/integration-test.ts` rather than `test`: it hands the test `redisUrl` and a `keyPrefix` of its own. Put every key the test touches under that prefix, so tests sharing the server never see each other's keys; never build a prefix in the test.
- The test opens its own client on `redisUrl`, with an `error` listener attached before it connects, and closes it in a `finally`, so a failed assertion leaves no open handle.
- Cut the connection with `startTcpProxy(redisUrl)` from `tests/tcp-proxy.ts`: point the instance at its `url`; `cut()` resets the live sockets and refuses new connections as a down server does, `restore()` accepts them again, `cutFor(milliseconds)` does both around a wait, and `stop()` goes in the `finally`. An integration or e2e test that needs a server with an evicting `maxmemory-policy` starts its own container with `startEvictingServer` from `tests/evicting-server.ts` (`isConfigDisabled` renames `CONFIG` away, as a managed service blocks it), which hands back its direct `url`, a `proxy` in front of it, and `stop()`; it is skipped with `skipIf(providedRedisUrl() !== undefined)`, so `NEXTASKING_TEST_REDIS_URL` still means no Docker.

## Engine scripts

- The engine lives in `src/engine/`: each Lua script is a TypeScript module exporting its source as a string (`enqueue-script.ts`), never a `.lua` file, because Next bundles the library and a file read at runtime would not ship. The engine prepends the shared library (`lua-library.ts`) and loads the result with `defineScriptCommand` (`script-commands.ts`).
- Test each script in one collocated integration file named after its module (`enqueue-script.integration.test.ts`), through the engine method that runs it, against the shared server. Assert on the method's typed reply and on the record and indexes, built with `engineKeysOf` from `src/engine/engine-keys.ts`; never write a key by hand as a string.
- Write a script test with `engineTest` from `tests/engine-test.ts`: it hands the body `engine`, `redis`, `keys` and `keyPrefix`, and runs the invariant checker after it. Compare everything stored under the prefix before and after a call that must write nothing with `storedValuesByKeyOf`.
- Make the lock tokens a fetch carries with `freshLockTokensOf(count)` from `tests/lock-tokens.ts`; the caller makes tokens, never the script. Lock runs for a test with `fetchedLockedRunsOf(context, count, limitsByTask)` from `tests/engine-test.ts`, and expire a lock without waiting with `expireLock(context, runId)`, which moves `lockedUntil` and the `locks` score into the past together. Age an ended run with `backdateEndedRun(context, runId, duration)`, which moves its `finishedAt`, its read index score and its dedup entry's expiry back together, and a handed-back run with `backdateFirstFoundUnknownAt(context, runId, duration)`; the scripts read only the server's clock, so a test never waits out a retention or a dedup window. End many runs of a task with `endRuns(engine, task, runIds, "complete" | "fail")` from `tests/ended-runs.ts`.
- A load scenario draws its randomness from `seededRandomnessOfThisRun()` in `tests/seeded-random.ts` (`random`, `pick`) and passes its `seedMessage` to each assertion, so a failure prints the seed; `NEXTASKING_TEST_SEED` replays it.
- Test a library function no script calls yet with a probe: a script made of `LUA_LIBRARY` and a small body, run with `EVAL` in `lua-library.integration.test.ts`. `engine-keys.integration.test.ts` runs the library's key builders the same way and compares them with `engineKeysOf`; a key shape changes in both or the test fails.
- Read the server's clock with `serverInstantInMillisecondsOf` from `tests/server-instant.ts`, and bound a stored instant between a reading before and after the call. Fake only `Date` (`vi.useFakeTimers({ toFake: ["Date"] })`) to prove an instant does not come from the app's clock.

## Invariant checker

- `invariantViolationsOf(redis, keyPrefix)` from `tests/invariant-violations.ts` lists, as sentences, every way the engine's keys under the prefix disagree. The checks: each member of an index (`runs:<task>:<state>`, `pending`, `due`, `locks`, a waiting list) has a record in that state, of that task and key, with the score the record gives. Each slot set holds only executing runs of its key, and each executing run, of a limited task or not, is in its key's slot set. Each record sits in the read index and the engine structure of its state and nowhere else, and its task is in `tasks`. Each side key of a run (`payload`, `errors`, `steps`) has its record beside it. `schedules` matches the schedule records and their `nextFiringAt`. Dedup entries are not checked.
- End every engine test with `await expectNoInvariantViolations(redis, keyPrefix)`, after the body, so a test fails with the list. A test that corrupts the keys on purpose asserts on `invariantViolationsOf` instead.

## Worker loop

- The worker loop (`src/worker-loop.ts`) and the attempt it runs (`src/locked-run-attempt.ts`) are unit-tested against `createInMemoryEngine()` from `tests/in-memory-engine.ts`: the engine over plain data, with the same typed replies as the scripts, no Redis and no Docker. Its declared type lists exactly the methods it implements; add a method to it when the loop starts calling one.
- The in-memory engine reads `Date.now()` unless given `now`. Run a loop scenario under `vi.useFakeTimers()`, so `vi.advanceTimersByTimeAsync` moves the loop's ticks and the engine's clock together, and the test reads as a scenario: enqueue three runs, advance, expire a lock, advance.
- Hand the loop `engine.waitForWakeUp` as its wake-up wait: it returns when the engine's wake-up marker is armed, by the same transitions as the scripts, or at its timeout. Never wake the loop by hand.
- Assert on the engine's `calls` (every call with its method and request, so one tick is one `tick` call), on `storedRunOf(runId)` and `runIdsInState(state)`, and on the lines of `createRecordingLogger()`. `expireLock(runId)` moves a lock's expiry into the past, `backdateEndedRun(runId, duration)` ages an ended run and `backdateFirstFoundUnknownAt(runId, duration)` a handed-back run, as their script-side namesakes do; `holdCalls(method)` keeps that method's calls waiting until `release()`, for a round trip still running. To make the engine answer differently (a lost reply, a rejected call), wrap one method in the scenario rather than adding a switch to the engine.
- Keep the in-memory engine honest with the contract suite: `defineEngineContractTests` in `tests/engine-contract.ts` runs each transition the loop depends on against the in-memory engine (`tests/in-memory-engine.test.ts`) and against the scripts (`tests/engine-contract.integration.test.ts`), through a harness giving the engine, `expireLock`, `backdateEndedRun`, `backdateFirstFoundUnknownAt`, an instant already past, a run's state and the wake-up marker. A transition the loop starts relying on gets a contract case in the same PR; where the two engines disagree, the spec decides the script, the contract pins it, and the in-memory engine is corrected.
- Build a loop's or an attempt's definitions with `workerDefinitionsOf(tasks)` from `tests/worker-definitions.ts`.
- Hand the loop or the attempt its Redis outage seam with `createSimulatedRedisOutage(logger)` from `tests/simulated-redis-outage.ts`: the real `createRedisOutage` on a real outage tracker, so the `connection error` / `connection restored` pair is the one production writes, and a fake ready-wait. `startOutage()` and `endOutage()` play the client's `error` and `ready` events. Make the engine away with `engineAwayDuringOutage(engine, outage, "rejected" | "pending until the outage ends")`: the second is what ioredis does with an unanswered command. Simulate an out-of-memory reply by wrapping a method to answer `OUT_OF_MEMORY_REPLY`. Never start Redis for an outage scenario of the loop.
- Expect a tick's command replies with `repliedOf(reply)`, `REPLIED_EMPTY_PROMOTE` and `REPLIED_ONE_RENEWAL` from `tests/tick-replies.ts`.

## Worker processes

- Run a worker in a child process, with `startWorkerProcess` from `tests/worker-process.ts`, when the test must signal, SIGKILL or block it, or needs several workers. Never install signal handlers in the Vitest process: the child sets `NEXT_MANUAL_SIG_HANDLE`, the in-process workers don't.
- The child runs `tests/worker-process-entry.ts` under `tsx`: it applies the `timing` override from `src/worker-timing.ts` (give lock and stall interval 1–2 s), starts the worker with `startWorkerOptions`, and runs the tasks of `tests/worker-process-tasks.ts`. Add a fixture task there; it blocks its own event loop when the test needs it, since a blocked child takes no command.
- Dispatch from the test with `createWorkerProcessNextasking` (`tests/worker-process-nextasking.ts`). Assert on the child's `logLines`, parsed from its NDJSON stdout into the same shape as `tests/recording-logger.ts`, its `exited` code and signal, and the records its tasks write (`fixtureRecordsOf`, `tests/fixture-records.ts`). `stop()` it in a `finally`.
- Give a test that waits on stalls or shutdowns its own `timeout`.

## E2E harness

- The e2e project proves the library the way a consumer uses it: packed, installed by name, bundled by Next, started from `instrumentation.ts`. Its scenarios, its harness and its fixture app live in `tests/e2e/`; the fixture app, `tests/e2e/fixture-app/`, is the manual's example made real. Its `next.config.ts` is empty unless `NEXTASKING_E2E_STANDALONE=1`, which sets `output: "standalone"` and nothing else, as the manual says it needs; it never sets `serverExternalPackages`, so a missing entry would fail it. Its `register()` writes `app registered` once `startWorker()` has resolved, and its `onWorkerNotStarted` writes `app notified: worker not started` with the error's message as `reason` after a short await, without exiting; the fixture's logger writes `err` as `{}`, so assert on those lines rather than on `err`.
- `tests/e2e/global-setup.ts` runs once per run: it fails unless `dist/` exists (run `pnpm build` first; the gate's `build` stage precedes `test:e2e`), copies the fixture app into a fresh directory under the OS temp dir, `pnpm pack`s the root into that copy as `nextasking.tgz`, installs it with no lockfile, then copies the installed app, symlinks kept, rather than installing twice. It runs `next build` in the first copy, and in the second with `NEXTASKING_E2E_STANDALONE=1`, whose `.next/standalone` it copies out to a directory of its own and deletes the rest, so a standalone scenario never reaches the project's `node_modules`. Then it starts the server exactly as the integration harness does (`NEXTASKING_TEST_IMAGE`, `NEXTASKING_TEST_REDIS_URL`). Teardown stops the server and deletes every copy.
- The harness builds a copy; never run `next` in `tests/e2e/fixture-app` itself. `next build` and `next dev` rewrite `tsconfig.json` and write `next-env.d.ts`, `.next/` and, on recent versions, an `AGENTS.md` into the directory they run in.
- The fixture pins `next` to the floor of the peer range; `NEXTASKING_E2E_NEXT_VERSION` replaces that pin in the copy (`16.4.3`, `latest`). `latest` resolves through pnpm's minimum release age, so it can be one release behind npm's `latest` tag.
- Write a scenario with `e2eTest` from `tests/e2e/e2e-test.ts`: it hands the test `redisUrl`, `keyPrefix`, `fixtureAppDir`, `standaloneAppDir`, and `fixtureAppEnv`, the environment that points the fixture at that server, under that prefix, with the fixture's worker gate on (`NEXTASKING_WORKER=on`); `fixtureAppEnvWithWorkerOff` is the same with the gate off, for a process that only dispatches.
- Start every process the scenario needs from the harness, and `stop()` it in a `finally`. Scenarios run one file at a time.
  - `startNext` from `tests/e2e/next-process.ts` runs `next start` or `next dev`, and `startStandaloneServer` runs `node server.js` in the standalone directory, each on a free port, waiting until it answers.
  - Both are a `CapturedProcess` from `tests/e2e/captured-process.ts`: the process output, `exited`, and `stop()`, which sends SIGTERM and returns the exit, forced with SIGKILL after 10 seconds.
- Assert on what a consumer observes: HTTP responses, the process output, and the records the fixture's tasks write under the scenario's prefix (`fixtureRecordsOf` from `tests/fixture-records.ts`). Drive a server action as a browser without JavaScript does, with `submitServerActionForm`.
- Run the project alone with `pnpm build`, then `pnpm test:e2e`; it needs Docker, unless `NEXTASKING_TEST_REDIS_URL` is set, and the npm registry.

## Waiting

- Wait for an asynchronous outcome by polling it with `vi.waitFor` (retries a callback until it stops throwing) or `vi.waitUntil` (until it returns a truthy value), each with an explicit `timeout`. A fixed sleep is never a wait.
- `retry` is 0 in `vitest.config.ts`: a test that only passes on a second try is a failing test.
